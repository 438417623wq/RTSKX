# 第十四轮 · M4c 落地报告：从「能连上」到「像一个联机游戏」

M4b 做完之后，两台机器已经能对打一局了 —— 但流程是**「输 IP → 一握手就开打」**：
没有房间可挑、没有准备确认、打起来之后一句话都说不了，想认输只能退程序。

这一轮把这条路上剩下的窟窿补齐：

| 补的是什么 | 之前的症状 |
| --- | --- |
| **UDP 广播发现** | 另一台机器必须手动输 `192.168.x.x`，输错一位就是「连不上」 |
| **准备 / 开始** | 主机能在对方还在加载地图时就开局 —— 客户端一进来就已经在打了 |
| **对局内聊天** | 全程零交流，只能靠打 |
| **投降** | 想认输只能直接退程序，对方看到的是「与主机断开连接」 |
| **暂停** | 单机有暂停键，联机里按了只暂停自己那一边（客户端根本不跑模拟） |

## 二、★五个「不报错」的真 bug★

这一轮抓到的问题**全部**是「功能看着在、其实不对」这一类的。按危险程度排：

### 2.1 每一条中文聊天消息都会**丢掉最后一个字**

`Net.packet_chat()` 里有一段「截断可能把多字节汉字切成半个，要退到完整字符边界」的修补：

```gdscript
	var b := text.to_utf8_buffer()
	if b.size() > MAX_CHAT_BYTES:
		b = b.slice(0, MAX_CHAT_BYTES)
	# ⚠️ 缩进在 if 里面，**但语义上是无条件执行的**（当时就是这么写的）
	while b.size() > 0 and (b[b.size() - 1] & 0xC0) == 0x80:
		b.remove_at(b.size() - 1)
```

这个 `while` **写在了 `if` 块外面**。于是每一条消息都会被砍：

> UTF-8 里，**任何**多字节字符的最后一个字节都长成 `10xxxxxx`。
> 所以「最后一个是续字节就删」这个条件**永远成立** —— 它会把最后一个完整的字一路吃掉。

症状极其隐蔽：

- 只有**中文**消息末尾少一截（纯英文消息末字节是 `0xxxxxxx`，完全正常）；
- 少了的那半截在接收端变成 `�`（替换字符），看起来像「编码问题」而不是「截断问题」；
- 而 `MAX_CHAT_BYTES = 240`（≈80 个汉字）在正常聊天里**几乎永远碰不到**，所以「截断逻辑」看起来根本没被走过。

修法两条：

1. 修补只在**真的截断过**的时候做（挪进 `if`）；
2. 修补本身也不能这么写 —— 「用长度变量当扫描游标」是错的，要**先找到最后一个字符的起始下标**，再看它够不够长：

```gdscript
static func trim_partial_utf8(b: PackedByteArray) -> PackedByteArray:
	var n := b.size()
	if n == 0:
		return b
	var i := n - 1
	while i > 0 and (b[i] & 0xC0) == 0x80:
		i -= 1                     # 续字节 → 继续往前找前导字节
	var c := b[i]
	var need := 1
	if (c & 0xE0) == 0xC0: need = 2
	elif (c & 0xF0) == 0xE0: need = 3
	elif (c & 0xF8) == 0xF0: need = 4
	if i + need <= n:
		return b                   # 最后一个字符是完整的 → 原样保留
	return b.slice(0, i)           # 残字 → 切到它的前导字节之前
```

现在它是一个**纯函数**，测试直接钉死 6 个边界（完整串 / 切 1 字节 / 切 2 字节 / 只剩半字 / 纯 ASCII / 空数组）。

> **教训**：`while (最后一个是续字节) 删掉` 这种写法**看起来**在「退到字符边界」，
> 实际上在「删掉最后一个字符」。UTF-8 的续字节判据**不能**单独用来找边界 ——
> 它只能用来**往前找前导字节**，不能用来决定「要不要删」。

### 2.2 投降之后，结算界面被快照「顶回去」

投降是**会话层**决定：本端立刻结算，主机要一个来回才知道。
在这一个来回里，主机发出的快照仍然带着 `winner = -1`（它那边还没结束）。

而 `Net.apply_snapshot()` 原本是**无条件照抄**快照里的胜负：

```gdscript
	w.winner = r.u8r() - 1
	w.game_ended = w.winner >= 0
```

于是：**点了投降 → 结算界面弹出来 → 下一份快照（100ms 后）把它顶回游戏里。**
玩家看到的是「画面闪了一下又回到战场」，而且**不报错**。

修法：胜负是**单调**的 —— 一旦结算过，后面的快照不能把它复活。

```gdscript
	var snap_winner := r.u8r() - 1
	if not w.game_ended:
		w.winner = snap_winner
		w.game_ended = w.winner >= 0
		if w.game_ended:
			# 客户端不跑 step()，_check_game_over() 永远不会被调到，
			# 所以这个信号必须在这里补发 —— 否则客户端的结算界面永远不弹。
			w.game_over.emit(w.winner)
```

顺带补上了**客户端永远不弹结算界面**这个洞：客户端不跑 `step()`，
`_check_game_over()` 根本没机会被调用，`game_over` 信号也就永远不发。

> ★这一条的阳性对照**第一次打不红**★ —— 我最初写的断言是
> 「已经结束的对局不能再投降」，它能不能红取决于「主机那边结束时，
> 客户端手上是不是正好有一份 `winner=-1` 的旧快照」，而这个时机由网络时序决定。
> 撤掉守卫照样全绿。
> 改成**手工构造一份「主机还没收到投降时发出的那种快照」**再喂进去，才真的红（2 条）。

### 2.3 主机等待页上的「开始游戏」会**整个消失**

`lobby_ui_state()` 原本用 `session.is_in_lobby()` 判断「在不在房间里」。
但主机在**还没人来**的时候停在 `HOSTING`，不是 `LOBBY` —— 那个状态是
「客户端握手完成」之后才切的。

结果：主机开完房间，等待页上只有「取消并返回」。
玩家看不到「还要等对方准备」这条信息，只会觉得「怎么连开始按钮都没有」，
然后一直等。

修法：新增 `NetSession.lobby_ready()`，主机侧放宽成
`HOSTING or LOBBY`：

```gdscript
func lobby_ready() -> bool:
	if link.is_host():
		return state == State.HOSTING or state == State.LOBBY
	return state == State.LOBBY
```

### 2.4 搜索房间页里**每个房间都叫「?」**（只有截图能发现）

绘制房间行时读的是 `room.get("host", "?")`，而 `NetDiscovery` 收包时写进去的键是 `name`：

```gdscript
	# ⚠️ 键是 `name`（`NetDiscovery` 收包时写进去的名字），**不是** `host`。
	#    写成 `host` 的话 `.get("host", "?")` 走默认值 —— 每个房间的名字
	#    都变成「?」，而 IP / 地图 / 人数全是对的，看着像「对方没设名字」。
	draw_string(font, ..., _safe_name(String(room.get("name", "?")), 12), ...)
```

这个 bug **无头测试抓不到** —— `_draw_*` 在无头里跑不起来，而
「命中表」里存的 `label` 用的是另一个字段，两条路径刚好都「有值」，
所以断言全绿、界面全错。

> **修法不只是改一个键名**：把「房间行显示什么」抽成纯函数 `room_display()`，
> 让**绘制 / 命中 / 测试三边读同一份**。这样「显示成 ?」这类问题
> 才会被 `tests/Lan.gd` 直接钉住（新增 5 条：名字不是 `?` / 带端口 / 带地图 / 带人数 / 空房间回落）。

### 2.5 灰掉的「开始游戏」**永远不告诉你为什么灰**（同样只有截图能发现）

大厅页绘制按钮时，**点不动**的分支里写了 `continue`：

```gdscript
		if not on:
			draw_rect(r, Color(1, 1, 1, 0.04), true)
			draw_rect(r, Color(1, 1, 1, 0.10), false, 1.2)
			_draw_text_center(String(m["label"]), r, 17.0, Color(0.45, 0.48, 0.55))
			continue                    # ← 顺手把下面那段 hint 也跳过了
		...
		var hint := String(m.get("hint", ""))
		if hint != "":
			_draw_text_center(hint, ...)
```

**理由（`hint`）恰恰只在点不动时才需要** —— 而点不动走的正是那条 `continue`。
于是玩家看到的是一个灰键，没有任何解释，只能一直点。

> 这个 bug 更隐蔽的地方在于：**数据层是对的**。
> `lobby_actions()` 确实给灰键带了 `"hint": "等对方准备"`，
> `tests/Lan.gd` 也已经断言了 `hint != ""` —— 测试全绿，界面上一个字都没有。
> **数据和渲染是两件事，测了数据不等于测了画面。**

修法分两步：

1. 把「按钮画什么」抽成纯函数 `lobby_button_plan()`，绘制器照着执行、
   测试直接检查指令表 —— 这样「灰键必须带理由」才钉得住；
2. **修好之后又发现第二个问题**：理由画出来了，但**挤进了下面那个键**。
   按钮从下往上排，间距默认 12px，而那行小字有 16px 高 ——
   于是「等对方准备」正好压在「取消并返回」上。
   间距改成**按需留出**（有理由时 12 → 30px），并配一条
   「小字矩形不与下一个键相交」的断言。

阳性对照：

| 对照 | 改动 | 结果 |
| --- | --- | --- |
| H | `lobby_button_plan` 在点不动时把 `hint` 丢掉 | 1 红 |
| I | 间距改回固定的 12px | 1 红（**小字底 646 > 下键顶 640**，数字精确） |

## 三、广播发现：为什么它比看起来难

### 3.1 端口互斥：搜索和广播**不能同时开**

`Net.DISCOVER_PORT` 只有一份。所以 `_sync_discovery()` 一次只开一个方向：

```
搜索页（St.LAN_SCAN）→ 当客户端，收公告
大厅里且是主机（St.LOBBY + _authoritative）→ 当主机，发公告
其它情况 → 关掉
```

⚠️ **客户端进房间后必须停掉**：它绑着 `DISCOVER_PORT`，不停的话同一台机器上
再开第二个实例时两边都收不到公告 —— 而且没有任何报错，只是「房间列表永远是空的」。

### 3.2 记的是**公告里的端口**，不是收到包的源端口

```gdscript
	# ⚠️ 记的是**公告里的 `game_port`**，不是收到包的源端口 ——
	#    源端口是发送方的临时端口（实测是 49841 这种），跟游戏端口没关系。
	#    用错的话房间列表里每个房间的端口都是错的，玩家照着连永远连不上。
	var key := room_key(ip, int(a["game_port"]))
```

阳性对照：改成源端口 → **3 条红**。

### 3.3 列表满了要**踢最旧的**，不是拒收新的

```gdscript
		if not _rooms.has(key) and _rooms.size() >= MAX_ROOMS:
			# 列表满了：踢掉最旧的那条，而不是拒收新的。
			# 拒收新的会让「先来的一堆僵尸房间」把真房间永远挡在外面。
			_drop_oldest()
```

阳性对照：改成 `return` → 1 条红。

### 3.4 `set_info()` 必须**内容没变就什么都不做**

主机的公告内容（人数 / 是否开局）每帧刷新一次。`set_info()` 无条件广播的话
就是**每秒 60 条广播** —— 整个局域网被刷满，每台客户端都在做无谓的解码。

```gdscript
	if info == _info:
		return
```

### 3.5 四条阳性对照全部确认断言可证伪

| 对照 | 改动 | 结果 |
| --- | --- | --- |
| A | 去掉 magic 校验 | 1 红 |
| B | `ROOM_TTL` 放大到 600 秒 | 1 红 |
| C | 列表满了改成「拒收新房间」 | 1 红 |
| D | 用发包的**源端口**而不是公告里的 `game_port` | **3 红** |

UDP 测试最怕偶发，连跑三次全绿。

## 四、大厅流程：准备 / 开始

### 4.1 状态机多了一个 `LOBBY`

```
主机：HOSTING ──(对方握手完成)──→ LOBBY ──(主机点开始)──→ PLAYING
客户端：CONNECTING ──(收到 WELCOME)──→ LOBBY ──(收到 START)──→ PLAYING
```

⚠️ M4b 时 `session_ready` 的语义是「对局开始了」，M4c 起它变成
**「世界已就绪，可以进大厅画面了」**。改名的代价太大（`Main` 里接了一堆），
所以保留名字、改语义，并在信号定义处写清楚。

### 4.2 三个条件缺一不可

```gdscript
func can_start() -> bool:
	return state == State.LOBBY and _peer_ready and _client_ready
```

⚠️ `_peer_ready` 和 `_client_ready` **不是一回事**：

- `_peer_ready` = 「握手完成了，包能正常来回」；
- `_client_ready` = 「人坐在那儿、点了准备」。

合成一个字段的话，客户端一连上就自动算「准备好了」，
主机可以在对方还在加载地图的时候就开局。

### 4.3 主机和客户端的**主按钮语义不同**

```gdscript
static func lobby_actions(in_room: bool, host: bool, me_ready: bool, can_start: bool) -> Array:
	if in_room:
		if host:
			out.append({"act": "lan_start", "label": "开始游戏",
				"enabled": can_start, "hint": "" if can_start else "等对方准备"})
		else:
			out.append({"act": "lan_ready",
				"label": "取消准备" if me_ready else "我准备好了", ...})
	out.append({"act": "lan_leave", "label": "取消并返回", ...})
```

合成一个的话，客户端会看到一个**自己点不动**的「开始游戏」，
主机能看到一个「我准备好了」—— 两个人都不知道该干什么。

灰键要**看起来就点不动**，而且**给出理由**（`hint`）——
画成和可点的一样，玩家会一直点，然后以为联机坏了。

### 4.4 大厅里一份快照都不发

```gdscript
	if state != State.PLAYING or world == null or _client_peer == 0 or not _peer_ready:
		return
```

少了这个守卫，客户端会在「还没开局」的状态下被快照推着动 ——
玩家看到的是「刚进房间就已经打起来了」。

### 4.5 客户端侧也不能判「失联」

```gdscript
	if state == State.PLAYING:
		...
		_since_snapshot += delta
		if _since_snapshot > SNAPSHOT_TIMEOUT:
			_fail("与主机失去联系…")
```

⚠️ 大厅里**不能**判 `SNAPSHOT_TIMEOUT` —— 那时一份快照都还没发过，
`_since_snapshot` 从 0 开始涨，5 秒后就会把好好的连接判成「失联」。
症状是**「在大厅里等 5 秒就掉线」**。

心跳（`PING`）在大厅和对局里**都要发** —— 大厅阶段没有快照，全靠它证明对方还活着。

## 五、对局内：聊天 / 投降 / 暂停

### 5.1 暂停是**主机权威**的

```
主机：set_paused(v)   → 本地生效 + 广播
客户端：request_pause(v) → 只发请求，本地状态**不动**
主机收到 PAUSE → 自己裁决（本版本直接采纳）并广播
```

⚠️ 客户端调 `set_paused()` 直接返回 `false`。**允许**它改本地状态的话，
玩家会看到「我这边暂停了、主机那边还在打」—— 最坏的错觉，
因为客户端**根本不跑模拟**，它的暂停没有任何意义。

阳性对照：去掉 `not link.is_host()` 这个守卫 → **5 条红**，
其中「客户端本地没有被改掉」正好抓的就是这个错觉。

### 5.2 投降走和「基地被打光」**同一条结算出口**

```gdscript
func surrender(who: int) -> void:
	if game_ended:
		return
	game_ended = true
	winner = ENEMY if who == PLAYER else PLAYER
	game_over.emit(winner)
```

⚠️ 另开一个字段（比如 `surrendered_by`）的话，各处读的仍是 `game_ended` ——
症状是「投降后界面显示赢了，但世界还在跑」。

⚠️ 包里**不带认输方是谁**：收包方按 `remote_owner` 自己算。
带的话客户端能伪造「主机投降了」。

### 5.3 聊天包里**不带发送者名字**

```gdscript
## ⚠️ **包里不带发送者名字。** 名字由收包方按 peer 查自己的会话状态 ——
##    带名字的话客户端能冒充主机说话。
```

### 5.4 发送方**不会收到自己那条的 `chat_received`**

自己发的那条由 `Main` 在调用点直接上屏。让本端也走一遍信号的话，
两边要各自判断「这条是不是我发的」，很容易变成「自己说的话显示两遍」。

### 5.5 两个独立的限流计数器

```gdscript
const MAX_CMD_PER_FRAME := 32
## ⚠️ 和指令限流**同理但独立计数**。共用一个计数器的话，
##    「一边打仗一边打字」时聊天会把指令额度吃掉（反之亦然）——
##    表现成「打着打着某个操作突然没反应」，而且只在手快时复现。
const MAX_CHAT_PER_FRAME := 4
```

收发两侧各算一份：客户端自己的发送配额 + 主机对**收到的**聊天的配额
（防被改过的客户端刷屏）。

## 七、接下来的方案

按**「不做就会一直悬着」**排序，不是按技术难度。

### 7.1 M4d 第一优先：**真机验证**（必须最先做）

联机这条线从 M4a 到 M4c 写了 18 套测试、上千条断言，但**两台真设备从来没对打过一局**。
现在所有结论都建立在「单进程回环 + 无头断言」上，而真机上至少有四件事**测不出来**：

| 真机才会暴露的 | 为什么无头测不到 |
| --- | --- |
| 局域网广播在真实 WiFi 下收不收得到 | 路由器可能拦广播 / 有 AP 隔离 / 手机省电策略冻结 UDP |
| 8 秒连接超时够不够 | 真机握手要过 WiFi + 安卓网络栈，比回环慢得多 |
| 10 Hz 快照在真机上的体感 | 无头没有渲染帧，感觉不到「拖影」 |
| 触屏操作 + 聊天键盘的手感 | 无头点的是合成坐标 |

**做法**：用 `godot-android-export` 打两个 APK（同包名、不同 `versionCode` 也行），
装到两台机器，跑一遍完整流程：搜索 → 加入 → 准备 → 开始 → 打 → 聊天 → 投降。
把每一步的实际耗时和异常记下来。

### 7.2 M4e：让「卡」和「断」不再难受

| 项 | 症状 | 方向 |
| --- | --- | --- |
| **客户端预测** | RTT 高时点一下要等一个来回才动 | 本地先动、收到快照再校正（只对移动类指令做，建造/技能仍等主机） |
| **断线重连** | 掉一下就回菜单，没有重连窗口 | 会话加 `RECONNECTING` 状态 + 一个 15 秒的重连窗口 |
| **快照压缩** | 全量快照 10 Hz，单位一多带宽吃紧 | 增量 + 变长编码（只发变化的单位） |

## 八、一句话总结

M4b 解决的是**「字节能不能过去」**，M4c 解决的是**「过去之后玩家知不知道该干什么」**。

这一轮抓到的问题里，**没有一个会报错**：
聊天少一个字、结算界面被顶回去、主机看不到开始按钮、
大厅里等 5 秒掉线、客户端自己暂停自己、每个房间都叫「?」、
灰掉的「开始游戏」不给任何解释 ——
全都是「功能看着在、其实不对」，而且**只有把断言写在正确的判据上**才抓得到。

其中**两条只有截图能发现**（`_draw_*` 在无头里跑不起来）：
「房间名显示成 ?」和「灰键不说为什么灰」。
而截图能告诉你的只是「**哪里**不对劲」，「**错在哪个字段 / 哪条分支**」
还是要回到代码里逐行对 —— 这跟 M4b 那次「把『几乎占满』读成『溢出』」是同一类教训。

更值得记的是第五条：**它的数据层是对的**。`lobby_actions()` 老老实实给了理由，
测试也断言了理由非空 —— **测试全绿，界面上一个字都没有**。
数据和渲染是两件事，**测了数据不等于测了画面**。

**但所有这些都还没有在两台真机上验证过。** 这是下一步最该做的事。
