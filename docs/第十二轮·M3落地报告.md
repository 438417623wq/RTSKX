## 二、三层能力，只做前两层

```
user://mods/<mod_id>/
├── mod.json          元数据：名称 / 作者 / 版本 / 说明
├── skins/*.png       皮肤（可选）
└── data/*.json       数值覆盖（可选）：units.json / buildings.json / upgrades.json
```

### 脚本模组：**不做**

GDScript 热加载 = 任意代码执行。手机上玩家**无法审计**模组内容，一个「模组」可以静默读取 `user://` 下的一切 —— 包括设置、存档、日志。这个口子不值得开。

而且它和本项目的合规立场直接冲突：**模组不进 APK，全部由玩家自备**，所以引擎里不能有任何「加载并执行外部代码」的路径。

### 合规：模组只覆盖**已有**条目，不能新建

`apply_mod_patch()` 遇到未知 id 会 `push_warning` 并跳过。理由不是保守，是**新建一个单位要同时改 5 张表**（`UNITS` / `BUILDINGS[x].trains` / `BUILD_MENU` / `AIR_RULES` / `UPGRADE_CLASS`），缺任何一张都是**静默半成品** —— 造不出来、或者造出来吃不到攻防升级，都不报错。让模组作者在 JSON 里踩这个坑，等于让他们去查一个查不出来的问题。

### 合并是**逐字段**的，不是整条替换

```json
{"marine": {"hp": 60}}
```

只改 `hp`，`damage` / `range` / `speed` 全部原样保留。整条替换的话，模组作者少写一个字段就把单位弄成残废 —— 而症状是「这个模组装上之后陆战队员不打人」，跟「改血量」八竿子打不着。

### 加载顺序：后加载的赢

列表里靠下的模组覆盖靠上的。顺序**玩家可调**（`↑` / `↓`），所以「谁赢」是可解释、可预期的 —— 这比任何自动仲裁规则都好。

## 三、冻结机制：本项目风险最高的一处改动

`GameData.UNITS` 从 `const` 变成了可变字典。它正踩在一条老铁律上：

> *「buff 绝不改 `data` —— `data` 是 `GameData.UNITS` 的共享字典，改它污染所有同类型单位（含敌方）」*

可变之后，任何「顺手改一下 data」的代码都会**跨模组、跨对局**地污染全局，而症状是「有些单位数值莫名其妙」，既不崩也不报错。

**三道防线：**

| # | 防线 | 实现 |
| --- | --- | --- |
| 1 | 只有模组加载器能写 | 必须走 `apply_mod_patch()`，游戏逻辑不许碰 |
| 2 | `freeze()` 之后一切写入被拒 | `push_error` + 返回 `-1`，数值一个字节不动 |
| 3 | 测试钉死 | `tests/Mods.gd` 第 5 组 + 第 10 组 |

```gdscript
static func apply_mod_patch(patch: Dictionary, mod_id: String = "") -> int:
    if _frozen:
        push_error("[GameData] 数据表已冻结，拒绝写入（模组加载必须在 freeze() 之前）")
        return -1
    ...
```

**换句话说：可变是给模组开的口子，不是给游戏逻辑开的口子。**

`Mods.apply_all()` 的收尾固定是 `GameData.freeze()` —— 连「一个模组都没装」也照样冻。理由见测试第 10 组。

### `Mods.reload()` 这个名字是个陷阱

M3 第一版把应用函数叫 `reload()`，结果调用方拿到的是 `Resource.reload()` 的返回值 `0`，**函数体一行都不执行，也不报任何错**。

`Mods` 作为 GDScript 资源对象继承了 `Resource` 的全部实例方法，同名静态方法被遮蔽。排查靠「在函数体第一行 print」才确认没进去。

> **教训**：`class_name` 的静态方法名要避开 `Resource` / `Object` 的实例方法 ——
> `reload` / `duplicate` / `get` / `set` / `call` / `free` / `to_string` …

已改名 `apply_all()`。

## 四、模组页 UI

`modrow` 是通用表单渲染器的第 7 种 `kind`。一行里放：

```
[✓] 高清贴图包  v1.2           someone    [↑] [↓]
```

- **勾选框 + 名称整行共用一个 act** —— 26px 的勾选框在手机上远低于 48dp 建议值，只让勾选框能点的话玩家得瞄着戳。
- **三种状态用颜色区分**，不用图标：正常灰 / **数值冲突**黄 / **缺 mod.json** 红。黄不是错误 —— 冲突不阻止加载（后加载的赢），只是要让玩家知道「装了新模组之后老模组好像没生效」是**正常的**。
- 对勾和排序箭头**用线段画**，不用 `✓` `▲` `▼` 字符 —— 字体缺字时 `draw_string` 会画成方块或空白，**且不报错**。

### 必须翻页，不能「让它自然变高」

设置页踩过这个坑：12 个设置项排成一条列表，面板算出 858px，而屏幕只有 720px，底部整块被推出屏幕 —— 而「逐项查在不在屏内」**查不出来**。

模组的数量更不可控（装 50 个完全可能），所以 `MODS_PER_PAGE = 5`，超出翻页。这个数字是算出来的，不是拍的：

```
可用高度 = 720 - FORM_HEAD_H(104) - 24 = 592
面板固定开销 = FORM_TITLE_H(78) + 底部留白(24) = 102
⇒ body 上限 490 = 两个 section 标题(64) + 46 × 行数 ⇒ 最多 9 行
本页固定占 4 行（翻页 / 重新扫描 / 路径按钮 / 说明）
⇒ 模组行最多 5 行
```

测试对 **0 / 1 / 5 / 6 / 12 / 30** 个模组逐个验**面板本身**在屏内。

模组目录的绝对路径放在**副标题**里 —— 副标题画在面板之上，**不占面板高度**。

### 纪律：模组根目录必须换到 `user://mods_test`

用真的 `user://mods` 的话，测试造出来的假模组会被**后续所有套件**的 `scan()` 扫到 —— 症状是「别的套件莫名其妙多出几个模组」，完全无从排查。

### 纪律：真实点击要用 headless 的视口尺寸

`_menu_press()` 内部用的是 `get_viewport_rect().size`（没有 vp 参数），而 headless 下那是 **1280×1280**。用真机尺寸 `1280×720` 取出来的矩形拿到 1280×1280 的表里去命中，会落到**完全不相干的行**上 —— 而断言照样有 PASS 有 FAIL，看起来像逻辑 bug，其实是坐标口径不一致。

（`tests/Menu.gd` 也是这个套路：按 `vp` 点，按 `DEVICE_SIZES` 验尺寸。）

### 三次阳性对照（回退代码确认断言真的会 FAIL）

## 六、★抓到的两个真 bug★

### bug 1：`DirAccess.open("user://…")` 恒返回 `null`

**这是本轮最有价值的发现，因为它让整个模组系统在真机上等于不存在。**

实测（Godot 4.7.2 / Windows）：

```
DirAccess.open("res://assets")                                  -> true
DirAccess.open("user://")                                       -> false   ← 
DirAccess.open("user://mods")                                   -> false   ← 
DirAccess.open(ProjectSettings.globalize_path("user://mods"))   -> true    ← 
FileAccess.open("user://settings.cfg")                          -> true
```

`res://` 正常、`FileAccess` 正常，**只有 `DirAccess` + `user://` 这个组合坏**。

后果全是静默的：

- `Mods.scan()` 一个模组都扫不到 → 玩家装了模组，列表里空空如也；
- `GenTex.ensure_skin_dir()` 里的 `DirAccess.open("user://")` 恒为 null ⇒ `d.make_dir("skins")` 永远不执行 ⇒ **`user://skins/` 目录从来没有存在过**（实测确认），而 README 里还写着「把 PNG 放进这个文件夹」；
- 全程**不报任何错**、退出码 0。

修法：**一律 `ProjectSettings.globalize_path()` 之后再 `open`**。

```gdscript
static func open_dir(p: String) -> DirAccess:
    return DirAccess.open(ProjectSettings.globalize_path(p))
```

> **新铁律**：本项目**不许直接 `DirAccess.open("user://…")`**。
> `make_dir_recursive_absolute("user://…")` 是**正常**的，别一起改了。

### bug 2：`Mods.set_enabled()` 漏了 `_rebuild_owners()`

`_owners`（字段级归属）只统计**启用中**的模组，但 `set_enabled()` 改完 `enabled` 之后没重算。

症状：**禁用掉冲突的一方之后，黄框还挂着**（「数值冲突 ×1」），玩家照着提示去排查，却怎么都找不到第二个模组 —— 因为那个模组已经被自己禁用了。

`move()` 和 `from_json()` 都调了 `_rebuild_owners()`，只有 `set_enabled()` 漏了。已补。

## 八、缺口与后续

1. **模组目录的绝对路径在 Windows 开发环境下是相对路径**（`./Godot/app_userdata/星海战火/mods/`）——
   这是本机 Godot 处于 self-contained 模式导致的，安卓上会是 `/data/user/0/<包名>/files/mods/`。不影响功能，但截图里的路径看着怪。
2. **没有「导入模组」按钮** —— 玩家得用文件管理器自己把目录拷进去。安卓 11+ 的分区存储让「选一个 zip 解压到 user://」变成一件要申请权限的事，留到 M4 之后。
3. **模组不支持新建单位 / 建筑**（见第二节），只支持覆盖已有条目。
4. **`MODS_PER_PAGE = 5` 在矮屏（1024×600）上仍然溢出** —— 和设置页的已知缺口同源（行高 46 已是触控下限，压不下去）。真要支持矮屏得加滚动，属于 M4 之后的事。
5. 方案第九节还有 5 个待拍板项，其中前两个是 M4 的前置：**局域网路线** / **大厅形态**。
