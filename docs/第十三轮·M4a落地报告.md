## 二、为什么地基要单独一期

因为它**不需要网络就能测**。

项目已有的无头测试基建可以直接覆盖「往返一致 / 尺寸上限 / 复用 buffer / 字节确定性」——
这些是**纯函数**，构造世界 → 编码 → 解码 → 逐字段比对，全程没有 socket、没有时序、没有不确定性。

一旦掺进 ENet，同样的断言就只能靠「起两个进程互连」来测：慢、脆、失败原因难定位。
**先把地基用纯函数钉死，M4b 调协议时才不会一动就崩。**

## 三、类型索引表：一处「只在联机时才出现」的静默错误

`type_idx` 只发整数。`"marauder"` 一个名字 8 字节，300 个单位就是 2.4 KB/帧 —— 必须换成索引。

索引表由**名字集合排序**得到，两端各自构建。只要两端的键集相同，算出的表就必然一致。

### 危险在哪

`GameData.UNITS` 现在是**可变字典**（M3 为了模组把它从 `const` 改掉了）。
如果索引表从 `UNITS` 构建，那么：

- 客户端装了模组、主机没装（或反之）→ 键集不同 → **索引整体错位**；
- 症状是「我的陆战队员变成了攻城坦克」；
- **不报错**，而且单机测不出来。

所以索引表一律从 `GameData.base_ids(kind)` 构建 —— 它只读 `_BASE_UNITS` / `_BASE_BUILDINGS`。

```gdscript
static func base_ids(kind: String) -> PackedStringArray:
    var keys: Array = []
    if kind == "units":     keys = _BASE_UNITS.keys()
    elif kind == "buildings": keys = _BASE_BUILDINGS.keys()
    keys.sort()          # ★必须排序★ 否则两端依赖字典插入序，一样会错位
    return PackedStringArray(keys)
```

> **新铁律**：任何「两端各自算一遍、必须算出同一个结果」的东西，来源只能是 `_BASE_*`，不能是可变副本。

## 四、快照格式

```
u8   type = SNAPSHOT
u8   proto_ver
u32  tick
f32  elapsed
u8   winner + 1                      # -1（未结束）→ 0
--- 双方全局 ×2 ---
u32  minerals, u32 gas, u16 supply_used, u16 supply_cap
--- 单位 ---
u16  count
  ×count: u32 id, u16 type_idx, u8 owner,
          f32 x, f32 y, f32 hp, f32 shield,
          u8 facing(0..255), u8 mode_idx, u8 flags, u8 carry, u8 harvest_state
--- 建筑 ---
u16  count
  ×count: u32 id, u16 type_idx, u8 owner,
          f32 x, f32 y, f32 hp,
          u8 progress(0..255), u8 flags,
          u8 queue_len, [u16 type_idx, u16 time_left_centis] × queue_len,
          [f32 rally_x, f32 rally_y]        # 仅当 flags 里有 BF_RALLY
--- 资源节点 ---
u16  count
  ×count: u16 idx, f32 amount           # 位置由同一个地图种子重建，只发「会变的量」
```

单位记录 **28 字节**。312 个单位 / 64 个建筑 / 37 个资源节点 → **10 407 字节 = 10.16 KB**，10 Hz 下行约 **102 KB/s**。

### 与方案的三处偏离（都是有意为之）

| 方案原文 | 实际实现 | 理由 |
| --- | --- | --- |
| 末尾发 `u32 vis_len + 位图` | **不发** | 客户端可以从「收到的自己单位」本地算出同一份迷雾。发位图是 3200 格 = 400 字节/帧的白送流量，而信息量是零 |
| 单位记录没有 `carry` / `harvest_state` | 补上（各 1 字节） | 农民在采集 / 返程要画不同姿态，不传的话客户端只能画成「站着不动的农民」 |
| `u16 queue_len` | `u8 queue_len` | 队列上限远小于 255（星际 1 是 5），省一字节 × 建筑数 |

### `reset_dynamic()`：幽灵墙

客户端每收到一份快照就**整个重建**动态内容。地形与资源节点由同一个种子生成，本来就在，不需要传输。

⚠️ **建筑占的格子必须解封**。不解封的话，一座建筑被拆掉之后，它占过的格子会永远保持「不可通行」——
地图上留下一串走不进去、也看不见的墙，而且**不报错**。

## 五、量化：一律 `roundi()`，不要 `int()` 截断

快照里所有连续量都要压成整数：`facing` → 1 字节、`carry` → 1/8 格、`time_left` → 1/100 秒、`progress` → 1/255。

第一版用了 `int()`（截断）。复算之后（Python 跑遍 0..2000 全量）：

| 分母 | 截断是否幂等 | 说明 |
| --- | --- | --- |
| `/255` | 是 | 恰好没有漂移点 |
| `/8` | 是 | 同上 |
| **`/100`** | **否** | `0.29 * 100` 在双精度下是 **28.999999999999996** → 截成 28 → 解回来 **0.28**，凭空少 10 毫秒 |

**截断是系统性向下偏的，偏差不会互相抵消。** 所以规则统一成一条：量化用 `roundi()`。
代价为零，而且让「解码结果再编码 == 原始字节」成为**构造性保证**。

> ⚠️ **这条的第一版测试样本是错的**：队列里放的是 `3.25` 和 `0.5` —— 两个**精确值**，
> 截断和四舍五入给出同样的结果，阳性对照实测**打不红**。
> 补了第三个条目 `0.29` 之后才真正钉住（回退 `roundi` → `1 红`）。
> **样本里必须放一个「会露馅的值」，否则断言只是在自我安慰。**

## 六、`build_progress` 的两种含义（口径错误）

`Building.build_progress` 在不同阶段是**不同的东西**：

- 施工中：已投入的**秒数**；
- 完工后：等于 `build_time`（40 / 26 / 24…）。

第一版直接发 `build_progress * 255`，于是完工建筑的 40.0 一路被 clamp 到 255、解回来全变成 `1.0`。
症状是「每个建筑往返后进度都不一样」—— 而且是**只有完工建筑**不一样，更容易被当成「这个字段不重要」放过。

正确做法是发 `progress_ratio()`（0..1 的比例，`Building` 里本来就有这个访问器），解码时再乘回 `build_time`：

```gdscript
# 编码
buf.u8(clampi(roundi(bb.progress_ratio() * 255.0), 0, 255))
# 解码
b.build_progress = float(prog) / 255.0 * b.build_time
```

这样 `complete` 的建筑解回来正好是 `build_time`，与 `setup(instant=true)` 的结果一致。

| 7 | **迷雾过滤** | 视野外的敌方单位**整条不发**；自己的单位一个都不掉；不过滤时都在（阳性对照） |

### ★四条「看起来在测、其实永远为真」的废断言★

这一期最值得记的不是 bug，是**断言本身的质量**。四条都是靠阳性对照暴露的：

| # | 第一版怎么写 | 为什么永远为真 | 改成什么 |
| --- | --- | --- | --- |
| 1 | 索引稳定性用 `apply_mod_patch({"units":{"marine":{"hp":999}}})` 构造 | 本版 `_merge_table` **明确拒绝新建条目**，只允许覆盖已有 id → **key 集合永远不变** | 直接往 `UNITS` 里塞一个排序在 `marine` 之前的假条目 |
| 2 | 幽灵墙用「同一份快照连收 10 次」 | 那 10 次占的是**同一批格子**，不累积 | **先占、再撤**：多放 3 座建筑 → 发快照 → 再发「没有那 3 座」的快照 → 3 格必须重新可通行 |
| 3 | 量化精度用 `3.25` / `0.5` 当样本 | 两个都是精确值，截断和四舍五入结果相同 | 补 `0.29`（唯一会露馅的一类值） |
| 4 | 迷雾的「远点」写死 `(120,120)` | 地图是对称的，**玩家基地有可能正好在左上角**，那点反而落在自家视野里 | 用**敌方基地**当远点，与地图布局无关 |

阳性对照实测（回退代码，确认断言真的会 FAIL）：

| 回退的东西 | 结果 |
| --- | --- |
| `reset_dynamic()` 里的解封那一行 | `通过 79 / 失败 2`（正好是那两条幽灵墙断言） |
| `ensure_type_table()` 改读 `GameData.UNITS`（排序后） | `通过 80 / 失败 2` —— 报错原文是「反索引仍指向 marine（实测 **marauder**）」，**正是那个症状** |
| `time_left` 量化 `roundi` → `int` | `通过 82 / 失败 1`（正好是 0.29 那条） |

> **纪律**：**没做阳性对照的断言，等于没写。** 一条永远为真的断言比没有断言更糟 ——
> 它会让人以为这块被测住了，于是改代码时不再回头看。

## 九、缺口与后续

1. **快照没做增量 / 压缩。** 102 KB/s 在局域网上没问题（WiFi 实测吞吐量是它的几十倍），
   但如果后面要上公网（M4d），这个数字必须降。手段：只发变化的单位 / 量化坐标到 1 格精度。
   **不在 M4b 的范围**——先保证能打起来。
2. **`Buf` 的「零分配」只钉住了「复用安全」**，钉不住「一次都不分配」。
   GDScript 观测不到 `StreamPeerBuffer` 的底层容量，`clear()` 之后 `size()` 归零是引擎行为。
   真要验证零分配得看 profiler。**断言写的是能测的那一半，没有假装测了另一半。**
3. **`fog_of()` 的缓存节流按 `elapsed` 算**，而 `elapsed` 是模拟时间。
   如果对局被暂停（`world.step()` 整段跳过），`elapsed` 不推进 → 缓存永不失效 → 迷雾不更新。
   **暂停时本来也不需要更新迷雾**，所以这是巧合地对。但 M4c 加暂停功能时要回头看这条。
4. **快照里没有「指令序号」**。方案第五节风险 4 的对策（客户端乐观执行 + 序号对齐）需要它，
   属 M4b。
5. **`Net` 只有 1 个 `PROTOCOL_VERSION = 1`**，还没有任何向后兼容策略。
   两端版本不一致时是「直接拒绝」——在局域网小规模场景下这是对的选择，
   但如果以后要支持「老客户端连新主机」，需要另设计。
6. **★客户端当 ENEMY 时没有迷雾★ —— M4b 必须先修这条。**
   `World.update_visibility()` 里写死了 `u.owner_id != PLAYER → continue`，
   `is_visible()` / `Main` 画迷雾也全部读 `world.vis`。
   也就是说**只有 PLAYER 这一个视角有迷雾**。

   1v1 局域网里主机是 PLAYER、客户端是 ENEMY —— 客户端拿不到任何迷雾，
   症状是「客户端整张地图要么全黑、要么全亮」，而且**不报错**。

   修法（约 5 行，但会牵动 `fog_of()` 的语义，所以没有顺手塞进 M4a）：
   给 `World` 加 `var local_owner := PLAYER`，`update_visibility()` / `is_visible()`
   一律读它，`fog_of()` 里的 `owner == PLAYER` 捷径改成 `owner == local_owner`。
   **必须有断言钉住**：把 `local_owner` 置成 ENEMY 后，敌方基地可见、己方基地不可见。

   > 之所以不在这一期做：M4a 没有客户端，改了也没人走那条路 ——
   > **没有调用者的代码就是没测过的代码**，留到有真实场景时一起做。
