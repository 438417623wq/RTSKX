# 建造体验与信息呈现方案（第八轮前哨）

> 起因：用户实测反馈三个问题
> 1. 农民去建房子的时候，**不知道是哪个农民在干活**
> 2. **建筑没有介绍**，长按显示或者常驻显示都行
> 3. 放一个建筑，**所有农民都跑过来了**，不应该只去一个吗？或者让我自己选
>
> 状态：**方案，未修改任何游戏代码**

---

## 一、问题定位

### 问题 3 是**真 bug**，而且根因很明确

**现场**：`World._update_buildings()`

```gdscript
var n_builders := _builders_near(b)          # ① 物理上站在工地旁边的农民数
...
elif not b.complete and n_builders == 0:
    _send_builder(b)                          # ② 派一个
```

**根因**：`_send_builder()` **不检查「是否已经有人接了这个工地」**。
它判断的是「工地旁边**站了几个**农民」—— 而正在赶路的那个农民，位置不在工地旁边。

**时序展开**（农民步行约 500px、速度 100px/s）：

| 时刻 | 事件 | 工地旁人数 |
|---|---|---|
| 0.0s | `cmd_build` 派农民 A | 0 |
| 0.5s | 判据成立 → 派 B | 0 |
| 1.0s | 判据成立 → 派 C | 0 |
| … | 每 0.5 秒派一个 | 0 |
| 5.0s | A 终于走到 | 1（停止派工） |

**5 秒里最多派出 10 个农民。** 这就是「所有农民都跑过来了」。

> **实测修正（写方案时估错了，代码验证后改）**：
> 工地本身不可能离基地太远 —— `can_place_building()` 有一条
> 「**必须建在己方建筑 190px 以内**」的建造半径约束。
> 但**农民通常在更远的矿点上采矿**，实际步行距离 400~600px 很常见
> （基地 190px + 矿点 300px 以上），所以 4~6 秒的步行时间是常态。
> 原稿写的「800px / 16 个农民」偏大，但量级和结论不变。

**为什么全是「闲着的」农民**：`_send_builder` 的候选条件里有
`if u.has_move_order or u.carry > 0.0: continue` —— 正在采矿的农民（`carry > 0`）
会被跳过，被派的都是空闲农民。所以玩家看到的是「我一放建筑，所有闲人全冲过去」。

**为什么这个 bug 之前没被发现**：`Smoke.gd` 只断言「建造指令可用」，
`Economy.gd` 只断言经济数字。没有任何测试断言过**建造者的数量**。

### 问题 1：建造者没有可视化

- `u.build_target` 只是一个逻辑标记，**渲染层从来没读过它**。
- 现状能看到的唯一线索是建筑身上那行 `建造中… 45%` 文字，
  但「是谁在把它推到 45%」完全没有呈现。
- 更糟的是：由于问题 3，工地周围经常围着一圈农民，
  玩家根本分不清哪个是干活的、哪些是刚被误派过来的。

### 问题 2：建筑/单位没有介绍

- `GameData.BUILDINGS`（18 个）和 `UNITS`（15 个）**都没有 `desc` 字段**。
- 全项目 `desc` 只出现 3 次，全在 `FACTIONS` 里（三族的定位描述）。
- 结果：玩家不知道「尖塔能出飞龙」「工程湾能升攻防」「医疗兵是干嘛的」。
  这些信息只存在于文档里，游戏里一个字都没有。

## 二、修复方案

### 2.1 建造者分配（对应问题 3）

#### ① 语义先纠正：把「按距离派工」改成「按指派派工」

新增两个函数，**取代**原来的 `_builders_near()`：

```gdscript
## 已经被指派到这个工地、且**已经到场**的建造者数 —— 决定建造速度
func _assigned_present(b) -> int:
    var n := 0
    var reach: float = b.radius() + 36.0
    for u in units:
        if u.dead or u.owner_id != b.owner_id or u.build_target != b:
            continue
        if u.pos.distance_to(b.pos) <= reach:
            n += 1
    return n

## 已经被指派到这个工地的建造者数（**含在路上**）—— 决定要不要补人
func _assigned_total(b) -> int:
    var n := 0
    for u in units:
        if u.dead or u.owner_id != b.owner_id or u.build_target != b:
            continue
        n += 1
    return n
```

`_update_buildings()` 改成：

```gdscript
var n_present := _assigned_present(b)     # 速度只看「到场的被指派者」
var was_complete := b.complete
b.update(delta, n_present)
if b.complete and not was_complete:
    ...
elif not b.complete and _assigned_total(b) == 0:
    _send_builder(b)                      # 没人接手才补一个
```

**关键变化**：判据从「旁边没人」变成「**没人接手**」。
在路上的人算「已接手」，所以不会再重复派工。

#### ② 让玩家能选（用户明确要求「或者自己选择嘛」）

`cmd_build` 加一个可选参数：

```gdscript
func cmd_build(type_id: String, pos: Vector2, owner: int, workers: Array = []) -> bool:
```

派工规则：

| 情况 | 行为 |
|---|---|
| 传了 `workers`（玩家选中了农民） | **用这些**，全部派去（选 3 个就 3 个去） |
| 没传 / 选中的不是农民 | 自动挑**最近的一个** |
| AI 调用 | 自动挑一个；`build_time >= 24` 的大型建筑挑 **2 个** |

`Main._confirm_place()` 传入 `world.selection` 里 `can_harvest()` 的单位。

**为什么「选中的全去」而不是「只去一个」**：
这是星际 1 的原版行为（选中 3 个 SCV 放建筑 → 3 个都去），
而且「我选了几个就几个去」正是用户说的「自己选择」。
不想多派人就别多选 —— 默认（没选）永远只派 1 个。

#### ③ AI 的补偿（必须做，否则平衡会漂）

**这是一个容易被忽略的连带影响**：现在 AI 的工地会因为**旁边采矿的农民**
被算进 `_builders_near`，从而拿到最高 2× 的建造速度。
改成「只算被指派者」之后，AI 会掉到 1×，**扩张节奏整体变慢**。

补偿方式：AI 的自动挑人按建筑规模给 1 或 2 个（见上表）。
`Building.update()` 里速度是 `minf(2.0, builders)`，所以 2 个就够拿满 2×。

⚠️ **这一项必须重跑 `bash tests/run_all.sh bal` 验证**。
如果三组对阵出现回归，回退方案是「只改派工逻辑、不改速度统计」
（即保留 `_builders_near` 给 `b.update()` 用，只用 `_assigned_total` 做派工判据）。

### 2.2 建造可视化（对应问题 1）

三处呈现，全部零新增美术：

**① 建造者头顶「扳手 + 进度环」**
在 `_draw_world()` 的单位循环**之后**追加一个 pass，
遍历 `build_target != null` 的存活单位：

- 头顶画一个半径 9 的圆环，弧度 = 建筑完成度，颜色 `#ffd166`
- 环心画一个极简扳手（两条 3px 短线交叉）
- 只有 `cam_zoom > 0.6` 时画 —— 缩到最小时画了也看不清，白费性能

**② 建造者 → 工地 的虚线**
只在「已指派但还没到场」时画（`distance > b.radius() + 40`），
复用 `Main.gd` 里已有的 `_dashed_line()`。
这样玩家一眼看到「我派的那个农民正在往哪走」。

**③ 工地进度条**
现在只有 `建造中… 45%` 一行文字。加一条 4px 细进度条，
并且**在没人的时候把文字变红**（`等待建造者`）——
这样问题 3 的修复效果也是肉眼可验证的。

### 2.3 建筑/单位介绍（对应问题 2）

#### ① 数据层：加 `desc` 字段（18 个建筑 + 15 个单位）

写「这个建筑是干什么的」，不是复述数值。每条 ≤ 16 字：

```gdscript
"barracks":        "训练陆战队员、劫掠者与医疗兵"
"engineering_bay": "研究步兵攻防与兴奋剂"
"factory":         "生产攻城坦克与秃鹫"
"spire":           "生产飞龙"
"evolution_chamber": "研究虫族攻防与甲壳"
"pylon":           "提供人口与能量场；神族建筑必须建在能量场内"
"forge":           "研究神族地面攻防与等离子护盾"
...
"medic":           "自动治疗附近友军；没有攻击力"
"siege_tank":      "可展开为攻城模式，射程与伤害大幅提升但不能移动"
```

#### ② 呈现方式：两处，形式不同

**A. 选中建筑/单位时 —— 常驻一行**（不用任何额外操作）

`Main.gd:1403` 的信息行从一行变两行：

```
工程湾 · 生命 850/850 · 轻点空地设置集结点          ← 原有，白色
研究步兵攻防与兴奋剂                                ← 新增，灰色小字
```

单位同理：`陆战队员 ×6 · 可扎兴奋剂`。

**B. 建造菜单 —— 长按 0.35 秒弹信息卡**

条目只有 96×84，icon + 名称 + 造价已经占满，**塞不下第三行**。
所以改成**长按弹卡**，松手即消失，完全不占布局：

```
┌────────────────────────────┐
│ 工程湾                      │
│ 研究步兵攻防与兴奋剂         │
│ ────────────────────────── │
│ 造价  125 矿               │
│ 建造  25 秒                 │
│ 生命  850 · 护甲 2          │
│ 前置  —                     │
└────────────────────────────┘
```

长按计时**复用编队行已有的机制**（`_group_press_time` / `_group_press_idx`
那一套已经验证可用，编队 1~6 就是这么实现长按存队的）。

## 四、测试方案：新增 `tests/Build.gd`

**这是本次最重要的产出。** 问题 3 是一个纯逻辑 bug，
「一队农民全被拉走」这件事没有任何现有测试能发现 —— 必须专门锁死。

| # | 断言 | 为什么重要 |
|---|---|---|
| 1 | 12 个农民 + 远处工地，跑 3 秒 → `build_target == b` 的单位**恰好 1 个** | **直接锁死问题 3** |
| 2 | 跑 10 秒全程，建造者数量**始终 == 1** | 防「先 1 个后变多个」的变体 |
| 3 | 传 3 个农民进 `cmd_build` → 恰好这 3 个被指派 | 验证「自己选择」 |
| 4 | 不传 → 被指派的是**最近的那个** | 验证默认行为 |
| 5 | 指派后清掉 `build_target` → 1 秒内自动补位 | 验证兜底仍然有效 |
| 6 | 建造速度：1 人 vs 2 人 → 2 人明显更快（且不超过 2×） | 锁住 `minf(2.0, builders)` |
| 7 | 完工后所有 `build_target == null` | 验证解绑 |
| 8 | 遍历 18 个建筑 + 15 个单位，`desc` 非空且 ≤ 24 字 | 防漏写 |
| 9 | 所有建筑的 `desc` 互不重复 | 防复制粘贴漏改 |

加上现有 6 套回归（`Matchup` / `Smoke` / `Economy` / `Touch` / `Upgrade` / `Ability`），
测试总数 194 → **约 205+**。

## 五、推进顺序

```
1. World 侧修 bug           ── _assigned_* + cmd_build(workers) + AI 补偿
        ↓
2. tests/Build.gd 第 1~7 项 ── 先把 bug 锁死，再动 UI
        ↓
3. GameData 加 desc          ── 纯数据，零风险
        ↓
4. UI：信息行 + 长按信息卡    ── 信息呈现
        ↓
5. UI：建造者标记 + 虚线 + 进度条
        ↓
6. tests/Build.gd 第 8~9 项 + 全量回归 + Shot 截图核对
        ↓
7. bash tests/run_all.sh bal ── 验证 AI 建造速度补偿是否到位
        ↓
8. 重打 APK
```

第 1 步和第 2 步必须连在一起做 —— **先写测试再修 bug 会失败，先修 bug 不写测试会复发**，
这两件事是同一个原子改动。

第 7 步不能省：这次动了建造速度的统计口径，属于会牵动平衡的改动。

## 六、需要你拍板的三个点

### 1. 选中多个农民时，是全部去还是只去一个？

| 方案 | 说明 |
|---|---|
| **A（推荐）** | 选中的全去 —— 和星际 1 一致，也是「自己选择」的自然结果；默认（不选）只派 1 个 |
| B | 永远只派最近的一个 —— 操作最省，但玩家选中的其他农民会「不听话」 |

### 2. 建筑介绍怎么显示？

| 方案 | 说明 |
|---|---|
| **A（推荐）** | 选中时常驻一行（不用操作）**＋** 建造菜单长按弹卡（信息更全） |
| B | 全部常驻 —— 建造菜单塞不下，只能砍掉造价行，不推荐 |
| C | 全部长按 —— 信息藏得深，新手还是找不到 |

### 3. 要不要同时给 15 个单位也加 `desc`？

推荐**加**。数据结构完全一样、成本几乎为零，
而且「医疗兵是干嘛的」「攻城坦克怎么用」现在游戏里也没地方看。

## 七、与第八轮（空军）的关系

这份方案**不占用第八轮的名额**，它是「体验补漏」而不是「新维度」：

- 第八轮的主题仍是**空中维度**（飞行单位 / 对空对地判定 / 防空建筑）
- 本方案第 2.1 节动了建造速度统计口径，**必须在做空军之前收尾并跑完平衡** ——
  否则空军的平衡数据会混进一个建造速度的变量，出问题时分不清是哪个引起的
- 本方案的 `tests/Build.gd` 会成为后续所有轮次的安全网
  （空军加入后 AI 的建造顺序一定会改，那时候这套测试就是回归基线）

## 八、实施记录（已完成）

按推荐项全部落地。实际改动与方案有两处偏差，都是**实施中被代码证伪**的：

### 8.1 与方案的偏差

| 项 | 方案写的 | 实际做法 | 为什么改 |
|---|---|---|---|
| 到场判据 | 距离 ≤ `radius + 36` | `World.builder_arrived()`：**没移动指令** + 距离 ≤ 260 兜底 | 站位要过 `grid.nearest_free_world()` 吸附，AI 摆密时会被弹到 60~75px 外，按距离判**永远不到场** |
| 面板高度 | 未提 | `PANEL_H` 156 → 180 | 信息行从 1 行变 2 行，156px 塞不下（左列编队 + 快捷两行共 96px，右列训练 + 队列最高 110px） |

### 8.2 顺手挖出的两个真 bug（方案里没预见到）

**A. 到场判据错了 → 工地永久烂尾（比原报告的 bug 更严重）**

站位被地形吸附到 60~75px 外 → 不算到场 → 进度永远 0%；
而「已指派数 > 0」又让它不补人。**诊断实测：一局里 5 个工地同时烂尾一百多秒，
13 个农民里 8 个被永久占死（t=80 时 8/8 全在「建造中」），AI 经济整个停摆。**

修完这条之后，Ability 套件里「AI 会研究升级」从**永远研究不出来**
变成 `35s 造进化腔 / 113s 排进队列 / 168s 拿到 1 级` ——
所以那条断言一直失败不是别的原因，就是被这个烂尾 bug 压着。

**B. 新工地抢老工地的农民**

`cmd_build` 自动挑人时没排除 `build_target != null` 的农民：
新工地把老工地的建造者挖走 → 老工地烂尾、新工地也不会更快，
被挖走的农民**永远回不去**。加了一行过滤。

### 8.3 测试结果

| 套件 | 结果 |
|---|---|
| `tests/Build.gd`（新建） | **12 / 12** |
| `tests/Touch.gd` | **50 / 50**（+4：介绍卡不出屏 / 长按弹卡 / 长按不误触发放置 / 点任意处关闭） |
| `tests/Ability.gd` | **20 / 20**（「AI 会不会研究」拆成 3 条断言） |
| `tests/Shot.gd` | 17 张截图，无 SCRIPT ERROR（新增 `15_builder_badge` / `16_build_info`） |

### 8.4 工具发现

**`godot --headless --check-only --script res://xxx.gd` 能解析 `Main.gd`。**
用故意写坏的脚本验证过：能抓 Parse Error、未声明标识符、类型推断失败。
比开窗口跑 `Shot.gd` 便宜得多 —— 改完先过 `--check-only`，再跑 Shot 看画面。
（此前记的「`--import` 不解析 `Main.gd`」没错，但漏了这个选项。）
