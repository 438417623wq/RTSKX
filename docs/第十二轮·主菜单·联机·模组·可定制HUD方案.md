## 三、主菜单架构

### 3.1 状态机改动

现在只有 `enum St { MENU, PLAY, END }`。需要：

```gdscript
enum St { MENU, LOBBY, PLAY, END }
enum Page { HOME, SINGLE, LAN, SETTINGS, MODS }
```

`MENU` 状态下由 `Page` 决定画哪一页；`LOBBY` 是联机等待房间（和 `MENU` 分开，
因为联机时后台有网络轮询，混在菜单里会让「单人页面」也跑网络代码）。

### 3.2 关键设计：通用表单渲染器

**这是本轮最重要的一个决定。**

现在的痛点上一轮已经踩过：*「每加一个选择项要改三处，漏掉任何一处都是『点了没反应』且不报错」*。
上一轮用「一张表 + group 字段」缓解了**同一行**的选项，但每加**一整行**还是要改绘制 + 命中两处。

设置页有 20+ 个项，模组页有列表和开关，局域网页有输入框 —— 如果继续手写，会迅速失控。

所以：**一个通用的表单描述 + 一个渲染器**。

```gdscript
# 每个页面 = 一个描述字典
const PAGE_SETTINGS := {
    "title": "设置",
    "sections": [
        {"name": "画面", "items": [
            {"kind": "choice", "key": "render_scale", "label": "渲染缩放",
             "options": [["0.75","75%"], ["1.0","100%"], ["1.25","125%"]]},
            {"kind": "toggle", "key": "shake", "label": "屏幕震动"},
        ]},
        {"name": "音频", "items": [
            {"kind": "slider", "key": "sfx_volume", "label": "音效音量", "min": 0.0, "max": 1.0},
            {"kind": "slider", "key": "music_volume", "label": "音乐音量", "min": 0.0, "max": 1.0},
        ]},
    ],
}
```

渲染器 `form_layout(page, vp) -> Array` 返回 `[{rect, kind, key, value...}]`，
**绘制、命中、测试三边读同一份** —— 和 `menu_option_rects` 完全同构，只是数据驱动。

好处：
- 加一个设置项 = 加一行数据，**不动绘制也不动命中**
- 无头测试可以遍历所有页面断言「每一项都在屏幕内、都能被命中」
- 模组页的列表、局域网页的输入框都能用同一套

### 3.3 页面导航

- 每页左上角「← 返回」，右上角显示标题
- 用**页面栈**（`_page_stack: Array[Page]`）而不是单变量 —— 模组页要能弹出「导入确认」子页，
  返回时回到模组页而不是主菜单
- `_draw_menu` 拆成 `_draw_page(vp)`，按当前页分派

## 四、局域网游戏 ★风险最高的一块

### 4.1 两条技术路线

| | 确定性锁步（Lockstep） | **主机权威 + 快照**（推荐） |
|---|---|---|
| 原理 | 所有端跑同一份模拟，只同步**指令**，按固定 tick 推进 | 主机跑唯一模拟，客户端发指令、收状态快照 |
| 带宽 | 极小（每 tick 几十字节） | 中（每快照 5~10 KB × 10 Hz ≈ 50~100 KB/s，局域网充裕） |
| 确定性要求 | **极高** | 无 |
| 天然附带 | 回放（记录指令流即可） | 无 |

### 4.2 为什么推荐主机权威

1. **`World.step()` 吃全局 `randf()`** —— 地图生成、AI 决策都在用。改成确定性 RNG 要动地图生成器与 AI 两处，回归面极大。
2. **arm64 真机 与 x86_64 模拟器混联时浮点可能不一致** → 锁步会**静默分叉**：两端画面越走越远，而且**不会有任何报错**。这和项目里踩过的「菌毯没铺 → 虫族 AI 变笨」「河道被岩石堵死 → 两岸孤岛」是同一类坑。
3. 项目已经「逻辑与渲染彻底分离」，`World` 是纯数据对象 → 序列化成本低。
4. 局域网（同一 WiFi，RTT < 10ms）带宽完全够用。

### 4.3 协议设计（主机权威）

```
传输   ENetMultiplayerPeer（Godot 内置 UDP）
发现   PacketPeerUDP 广播到 255.255.255.255:<PORT>，同网段自动发现房间
指令   客户端 → 主机：cmd_move / cmd_build / cmd_train / cmd_ability …
快照   主机 → 客户端：每 100ms 一次
       单位：id / 类型 / 位置 / 朝向 / 血量 / 状态位
       建筑：id / 类型 / 位置 / 建造进度 / 队列长度
       全局：双方资源 / 人口 / 计时
客户端 收到快照后插值渲染；本地指令**乐观执行**，下个快照到达时校正
```

### 4.4 三个必须提前说清的风险

**风险 1：迷雾会被绕过。**
每个玩家的视野不同。如果主机广播「完整世界状态」，客户端只要解包就能看到全图 ——
**等于内置作弊**。修法：主机按每个客户端各自的 `vis` 数组过滤后再发。
代价是主机要维护 N 份可见性过滤，且迷雾外的单位**不能发坐标**（否则仍可推断）。
**这条在实现顺序上必须排在很前面** —— 后补的话整个快照格式都要重写。

**风险 2：序列化不能每帧分配。**
`World` 现在**没有任何序列化方法**。几百个单位 × 每 100ms 一次，
如果每帧 `to_dict()` 造新字典，GC 压力会让手机掉帧。
必须用 `PackedByteArray` 手工打包（定长字段 + 变长只用于 id）。

**风险 3：客户端手感。**
主机权威 = 客户端操作要等一个来回。局域网 RTT < 10ms，加上 100ms 快照间隔，
平均约 35ms —— 点一下地面，单位 35ms 后才动，**在手机上能感觉到**。
缓解：客户端本地也跑一份「预测模拟」，收到快照硬同步。
但这会引入「预测与实际冲突」的抖动，**建议 M4 先不做预测**，先保证「能打起来」，再调手感。

### 4.5 建议的最小可用范围

- **2 人**（不是 4 人）
- **手动输 IP 直连**（不做房间列表广播 —— 那是纯 UI 工作量，可以后补）
- **不做断线重连**（掉线即结束）
- **不做观战**

先让两台手机能真的对打起来，再谈体验。

## 五、模组系统

### 5.1 三层能力（由浅入深）

| 层 | 内容 | 现状 |
|---|---|---|
| **皮肤模组** | `user://mods/<id>/skins/*.png` 覆盖单位/建筑贴图 | **已有 80%**（`GenTex.load_skin` 现在就支持 `user://skins/`） |
| **数据模组** | `user://mods/<id>/data/*.json` 覆盖单位/建筑/升级数值 | 需要架构改动，见下 |
| **脚本模组** | 热加载 GDScript | **建议不做**（理由见下） |

### 5.2 数据模组的架构改动（有一个必须防的坑）

`GameData.UNITS` / `BUILDINGS` 现在是 `const`。要支持模组覆盖，得改成「加载后合并」：

```gdscript
static var UNITS := _BASE_UNITS.duplicate(true)   # 启动时拷贝一份
static func apply_mod(m: Dictionary) -> void: ... # 合并覆盖
static func freeze() -> void: ...                 # 全部模组加载完后冻结
```

⚠️ **必须配「冻结」机制**，否则会放大一个已经存在的风险：
记忆里的铁律是 *「buff 绝不改 `data` —— `data` 是 `GameData.UNITS` 的共享字典，改它污染所有同类型单位（含敌方）」*。
`UNITS` 一旦从 `const` 变成可变，任何「顺手改一下 data」的代码都会**跨模组、跨对局**地污染全局。
修法：`freeze()` 之后所有写操作 `push_error` 并拒绝，且**写一条测试**钉死「冻结后写 UNITS 会被拒」。

### 5.3 模组包结构

```
user://mods/<mod_id>/
├── mod.json          元数据：名称 / 作者 / 版本 / 依赖 / 加载顺序
├── skins/*.png       皮肤（可选）
└── data/*.json       数值覆盖（可选）
```

- 加载顺序：按列表顺序，**后加载覆盖先加载**
- 冲突检测：两个模组改同一个字段时，在列表里标黄提示
- 合规：模组**不进 APK**，全部由玩家自备 —— 与现有「零外部素材」策略完全一致

### 5.4 为什么不做脚本模组

GDScript 热加载 = **任意代码执行**。手机上玩家无法审计模组内容，
一个「模组」可以静默读取 `user://` 下的一切。这个口子不值得开。

## 七、HUD 可定制（向 WC3 靠齐）

### 7.1 先看 WC3 是怎么排的

魔兽争霸 3 的界面：
- 底部一条命令面板：**左下小地图** + 中央选中单位头像/血条 + **右下 4×3 命令卡**
- 资源（金/木/人口）在命令卡正上方
- **没有顶栏**
- 布局**固定不可拖**，但快捷键可以自定义（`CustomKeys.txt`）

我们要做的比 WC3 **更灵活** —— 因为目标是手机：**左手拇指够不到右下角**。
WC3 的固定布局在触屏上就是灾难，所以「可拖动」不是锦上添花，是**必需**。

### 7.2 模块划分

| 模块 | 现在的位置（硬编码处） | 允许吸附 |
|---|---|---|
| `res` 资源/人口/计时/敌基地 | 顶栏左侧 | 上边 |
| `sysbtns` 暂停/速度/说明/音效 | 顶栏右侧 | 上边 |
| `minimap` 小地图 | 左下（浮在面板上方） | 四角 |
| `cmd` 指令区（建造/技能/停止） | 面板右侧 | 下边 / 右边 |
| `queue` 生产队列 + 编队行 | 面板中部 | 下边 |
| `info` 信息行 + 快捷行 | 面板左侧 | 下边 |

### 7.3 配置项

每个模块：`anchor`（9 宫格之一）+ `offset`（相对锚点的逻辑像素偏移）+ `scale`（三档）+ `visible`。

**缩放档位锁死三档**（0.85 / 1.0 / 1.15），不给连续值 —— 理由：
最小按钮是 `BTN_BUILD_W=96 × BTN_BUILD_H=84`，0.85 档是 81.6×71.4，仍高于触控下限；
再往下就会破线（记忆里的教训：*46 逻辑像素在 2400×1080 上只有 4.3mm，不到 Android 48dp 建议值的六成*）。

### 7.4 编辑模式交互

- **入口**：设置 → 界面 → 「编辑布局」；或对局中**长按顶栏 1 秒**
- 编辑时：每个模块画半透明底 + 边框 + 拖动柄；屏幕画出 9 宫格吸附参考线
- 拖动跟手，松手时若模块中心落在某宫格内 → 吸附并换算 `offset`
- 底部固定一排「重置 / 保存 / 取消」
- ⚠️ **编辑模式下世界暂停** —— 否则一边调布局一边被 AI 打

### 7.5 实现要点（把现有架构接上去）

现有 7 个布局函数全部改成读配置：

```gdscript
func _panel_rect(vp: Vector2) -> Rect2:
    return _mod_rect("info", vp)      # 内部：anchor + offset + scale
```

**关键约束：默认配置必须精确等于现在的硬编码坐标。**
这样 74 条触屏断言**一条都不用改**就能继续通过 —— 这是「改动是否破坏了现有行为」的免费判据。
如果默认配置对不上，那 74 条会红一片，反而掩盖真正的回归。

### 7.6 三个已知的坑（提前写在这里）

1. **`PANEL_H` 不再是全局常量。** 它现在被小地图和建造菜单推导。模块化后「面板」不再是一条全宽贴底的横条 → 小地图的「相对面板」定位要改成「相对 `minimap` 自己的锚点」，建造菜单要改成「相对 `cmd` 模块」。
2. **建造菜单的展开方向要跟着 `cmd` 走。** 它现在是「从右下角向上长出来」。`cmd` 被拖到左上角后，还向上长就会长出屏幕 → 要按 `cmd` 所在象限决定展开方向。
3. **模块重叠不做硬禁止。** WC3 允许自由摆放，玩家可能故意让面板盖住小地图。编辑模式里给**黄色警告描边**即可，不阻止。

## 九、需要你拍板的五个点

### 1. 局域网走哪条路？
- **推荐**：主机权威 + 快照。不需要确定性，避开浮点分叉这个无底洞
- 另一条：确定性锁步。带宽极小、天然带回放，但要求浮点完全一致 —— 真机 arm64 与模拟器 x86_64 混联会静默分叉

### 2. 局域网先做哪种大厅？
- **推荐**：手动输 IP 直连 2 人。先把「能打起来」做出来
- 另一条：带房间列表的广播发现（同网段自动看到房间）。体验好，但那是纯 UI 工作量，可以后补

### 3. 模组要不要允许脚本？
- **推荐**：不做。只做皮肤 + 数据。理由：GDScript 热加载 = 任意代码执行，手机上无法审计
- 另一条：允许，但要求玩家手动确认风险

### 4. HUD 编辑做到哪一档？
- **推荐**：拖动 + 吸附 + 缩放三档 + **显示/隐藏单模块**（隐藏是零成本的，等于把模块的 `visible` 置 false）
- 另一条：只做拖动 + 吸附（更简单，但玩家没法关掉不用的模块）

### 5. 菜单要不要「载入存档」入口？
存档系统本身还没做（方案第六节明确列为不做）。选项：**先留灰掉的入口**（提示「开发中」）或**整个不出现**。

2. 新增 UI 一律走**纯函数坐标 + `_ui_hit` 登记**，让无头测试能覆盖
3. 新增设置项要有断言钉住「改了它，行为真的跟着变」（不能只测「存进去了」）
4. 布局默认值必须 == 现有硬编码值，用 74 条触屏断言当免费回归判据
5. 改完先 `--check-only --script res://xxx.gd` 过语法，再跑 `tests/Shot.gd` 看画面
