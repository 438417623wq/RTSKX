### 1.3 地形只有一种高度

`Grid.gd` 的地形枚举是三种**平面**类型：

```gdscript
enum Terrain { GROUND, ROCK, CHASM }
```

且 `set_terrain()` 把 ROCK 和 CHASM **一视同仁**地写成 `blocks = 1`：

```gdscript
blocks[i] = 1 if t != Terrain.GROUND else 0
```

也就是说：**整个游戏世界是平的**。没有「层」的概念，没有坡道，没有「站在高处打低处」。

### 1.4 地图是固定种子的随机色块

`World._generate_map()` 用硬编码种子 `20260920` 画一堆岩石，双方出生点直线对称（`x=6` 与 `x=map_w-6`），中间一簇中立矿。地图尺寸固定 `64 × 40` 格 × 24px = **1536 × 960**，写死在 `Main.start_game()`。

没有地图选择，没有对称性设计，没有策略要点（没有坡道、没有高地矿区、没有可堵的咽喉）。

### 1.5 一句话总结

**引擎和系统骨架已经齐了，缺的是「战术深度」。**

现在玩一局的实际体验是：平地上框选部队 → A 过去 → 拼数值。中后期没有决策（矿物多了只能堆兵），没有操作（单位没有技能），没有地形（地图是平的），没有制空权（飞龙其实是在地上跑的）。

## 二、缺口清单（按「影响 × 改动面」排）

| # | 缺口 | 玩家影响 | 改动面 | 依赖 |
|---|---|---|---|---|
| 1 | **科技升级** | ★★★★ 中后期没决策、经济没出口 | 小-中 | 无 |
| 2 | **单位技能** | ★★★★ 操作只有「A 过去」，没有深度 | 中 | 复用 UI 命中表 |
| 3 | **空军 + 防空** | ★★★★ 没有空中维度，飞龙名不副实 | 中 | 无（寻路走分支） |
| 4 | **高地 / 悬崖** | ★★★★★ 星际最核心的战术要素 | **大** | 需重做地图生成 |
| 5 | **虫族菌毯** | ★★★ 虫族失去核心特色 | 小-中 | 无 |
| 6 | **建筑挂件** | ★★ 人族建筑树不完整 | 小 | 依赖升级系统 |
| 7 | **音频面板** | ★★ 只有开关，没有音量 | 小 | 无 |
| 8 | **对局流程** | ★★★ 单张固定地图、无重播、无存档 | 中 | 依赖地图生成 |

### 为什么把「高地」放在第四而不是第一

高地的**影响最大**，但**改动面也最大**，而且是唯一一个会牵动**全部子系统**的改动：

- `Grid` 要加 `level` 层，`blocks` 的单字节语义要拆成「通行性 + 层高」
- A\* 要加「换层只能走坡道」约束
- 视野 `_mark_visible` 要加「高地挡住低地视线」
- 索敌与弹道要加「低地打高地」规则
- `can_place_building` 要检查同层
- 渲染要画层次与坡道，小地图要体现层次
- **地图生成要重新设计**（对称、坡道、高地矿区）

而且它需要一个前提：**兵种和升级足够丰富**。否则只是把「平地对冲」换成「坡道对冲」，玩家感知不到质变。

所以路线是：**先用升级 + 技能把「决策与操作」补齐，再做空军打开维度，最后动地形。**

## 四、第七轮详细方案

### 4.1 科技升级

#### 4.1.1 数据结构（`GameData.gd`）

新增 `UPGRADES` 表。**升级分两类**，这个区分很关键：

```gdscript
const UPGRADES := {
    # ---------- 等级链：可叠加，每级 +1 ----------
    "infantry_weapons": {
        "name": "步兵武器", "faction": "terran", "kind": "level", "max_level": 3,
        "effect": "attack", "applies_to": "infantry",
        "levels": [
            {"cost_m": 100, "cost_g": 100, "time": 60.0},
            {"cost_m": 175, "cost_g": 175, "time": 75.0},
            {"cost_m": 250, "cost_g": 250, "time": 90.0},
        ],
        "requires": "engineering_bay",
    },
    "infantry_armor": { ... "effect": "armor", "applies_to": "infantry" ... },

    # ---------- 解锁型：只升一次，作用是给单位开一个技能 ----------
    "stim_pack": {
        "name": "兴奋剂", "faction": "terran", "kind": "unlock", "max_level": 1,
        "unlocks": "stim", "applies_to": "infantry",
        "levels": [{"cost_m": 100, "cost_g": 100, "time": 70.0}],
        "requires": "engineering_bay",
    },
}
```

**等级存在阵营上，不存在单位上。** 理由：

- SC1 的攻防升级就是**全族共享**的，升完立刻作用于所有现有和未来的单位
- 存 `factions[owner]["upgrades"]` 就不用在单位创建时同步、不用遍历全军队
- 伤害计算时按 `owner_id` 查表即可

```gdscript
# World
factions[PLAYER]["upgrades"] = {}   # {"infantry_weapons": 2, "infantry_armor": 1}
```

#### 4.1.2 单位分类（`GameData.UNITS` 加字段）

升级要知道「这个单位吃哪一套」。新增 `upgrade_class` 字段：

| 阵营 | 单位 | `upgrade_class` |
|---|---|---|
| 人族 | SCV / 陆战队员 / 劫掠者 | `infantry` |
| 人族 | 秃鹫 / 攻城坦克 | `vehicle`（第八轮跟军械库一起做） |
| 虫族 | 跳虫 | `melee` |
| 虫族 | 刺蛇 / 蟑螂 | `missile` |
| 神族 | 狂热者 / 龙骑士 | `ground` |
| 神族 | 执政官 | `none`（SC1 里执政官不吃攻防升级） |

#### 4.1.3 伤害公式改动

现有公式（`GameData.compute_damage`）：

```gdscript
return maxf(1.0, base * mult - target_armor)
```

改成（**加成加在 base 上，护甲加在 armor 上，保持先乘后减**）：

```gdscript
static func compute_damage(base, dtype, atype, armor, atk_bonus := 0, def_bonus := 0) -> float:
    var mult: float = DMG_TABLE.get(dtype, {}).get(atype, 1.0)
    return maxf(1.0, (base + atk_bonus) * mult - (armor + def_bonus))
```

两个可选参数带默认值 0，**所有现有调用点不用改**，只有 `Unit.take_damage` / `Building.take_damage` 传入加成。

> 注意：护盾也吃护甲升级（SC1 里神族护盾升级是独立的，但简化成吃护甲加成，第七轮先不做独立护盾升级……不，见下）。

神族的**护盾升级**单独做一条 `shield_upgrade`，`effect: "shield_armor"`，只作用于 `max_shield > 0` 的单位。这是神族特色，值得单独一条。

#### 4.1.4 研究执行 —— 复用 `Building.queue`

**不新增研究槽，复用生产队列**，条目加 `kind` 字段：

```gdscript
# Building.gd
func queue_item(kind: String, id: String) -> bool:
    if queue.size() >= 5:
        return false
    var t := 10.0
    if kind == "unit":
        t = float(GameData.get_unit(id).get("build_time", 10.0))
    else:
        t = float(GameData.upgrade_time(id, level))
    queue.append({"kind": kind, "id": id, "time_left": t, "total": t})
    return true
```

这么做**顺带实现了 SC1 的「一个建筑同一时间只能做一件事」**——研究和训练互斥。比新开一个研究槽更保真。

`World._try_produce()` 结算时分流：`kind == "unit"` → 出兵；`kind == "upgrade"` → 升 `factions[owner]["upgrades"]`。

#### 4.1.5 需要新增的建筑（3 个）

| 阵营 | 新建筑 | 造价 | 建造时间 | 作用 |
|---|---|---|---|---|
| 人族 | 工程湾 `engineering_bay` | 125 矿 | 25s | 步兵攻/防、兴奋剂的前置 |
| 虫族 | 进化腔 `evolution_chamber` | 75 矿 | 20s | 近战攻/远程攻/甲壳的前置 |
| 神族 | 熔炉 `forge` | 150 矿 | 22s | 地面攻/防/护盾的前置 |

#### 4.2.3 `Unit.gd` 新增字段

```gdscript
var energy := 0.0
var max_energy := 0.0
var ability_cd := 0.0
var buffs := {}                # {"stim": 剩余秒数}
var mode := "normal"           # 攻城坦克：normal / sieged
var mode_timer := 0.0          # 展开/收起剩余时间
```

**读取时叠加 buff，不改 `data`**。这是关键设计：`data` 是 `GameData` 的共享字典，**改它等于污染全局数据**。所以：

```gdscript
func speed() -> float:
    var s := float(data.get("speed", 90.0))
    if buffs.has("stim"):
        s *= float(GameData.ABILITIES["stim"]["buff"]["speed_mult"])
    if mode == "sieged":
        s = float(GameData.ABILITIES["siege"]["sieged"]["speed"])
    return s

func attack_range() -> float:
    if mode == "sieged":
        return float(GameData.ABILITIES["siege"]["sieged"]["range"])
    return float(data.get("range", 40.0))
```

`cooldown_time()` 同理吃 `cooldown_mult`。

#### 4.3.2 指令区插入技能按钮

选中单位后，指令区从右往左是「建造 / 采矿 / 攻击移动 / 全选同类」。技能按钮插在**最左**（离拇指最远，因为技能是低频但需要瞄准的操作）：

技能按钮的状态要能一眼看出：**可用 / 冷却中 / 能量不足 / 未解锁**。

### 4.4 AI 必须同步（否则平衡测试失真）

**这是最容易漏的一步。** 如果玩家能升攻防、AI 不能，玩家升满后会碾压，而且 `bal.gd` 跑出来的平衡数据全是假的。

`World._ai_economy()` 里加升级决策：

```gdscript
# 条件：有前置建筑 + 资源超过阈值 + 没有正在研究的升级
# 优先级：攻防升级 > 解锁技能
```

同时 `_ai_produce()` 要让 AI 会**用技能**（至少会用兴奋剂和攻城模式）。否则 AI 有技能不用，还是打不过。

### 9.2 与方案的三处偏离（都是实测后改的）

**① 建筑面板不做页签（推翻 4.3.1）。**
方案里担心「面板高 156px，加页签后条目区变矮」。实际做的时候发现：升级型建筑（工程湾 / 进化腔 / 熔炉）**没有 `trains`**，带训练的兵营 / 重工厂 / 尖塔**没有升级**——两类**永不共存**。所以按 `GameData.upgrades_for_building(b.type_id)` 是否为空直接分支即可，少一层页签交互、少一块布局，条目高度也不用从 72 压到 64。

**② 能量回复改成固定速率（原为「每秒回复最大值的 6%」）。**
百分比的问题是高能量单位回得太快：医疗兵 200 能量 → 12 点/秒，而治疗只花 1 点。能量形同虚设，测试里甚至出现「治疗了 3 次，能量从 200 还是 200」。
改为 `GameData.ENERGY_REGEN = 0.75` 点/秒（固定值，不再随上限缩放）。

**③ 新增一条施放闸门（方案里没有）。**
`can_use_ability()` 里加「**已处于该增益中就不能再施放**」。兴奋剂的 `cooldown` 是 0（SC1 里也是），`_ai_use_abilities()` 每帧都会来问一次——少了这道闸，10 点自伤会每 0.05 秒扣一次，整队陆战队员在 1 秒内被扎到 1 血。
症状具有极强的误导性：看起来像「AI 的兵特别脆」，而不是「技能被重复施放」。
buff 键名直接用技能 id，一条规则覆盖所有持续型技能。UI 侧同步加了「生效中 ×N」状态，否则玩家会以为按钮坏了。

### 9.3 两个值得记住的坑

**护盾升级的匹配不能凭印象写断言。**
我原本写「龙骑士吃护盾升级、狂热者不吃」——错了。神族单位在 SC1 里是**全员带护盾**的，狂热者也有 60 点。
改成数据驱动的断言（对全部 15 个单位逐一比对「有护盾 ⇔ 吃护盾升级」），实测 4 / 15 个。这类「凭印象写死断言」的测试比没有测试更危险，因为它会逼着你去改正确的代码。

**测「AI 会不会研究」必须给玩家一支守备队。**
诊断脚本（临时写的 `_diag_ai.gd`）显示：AI **确实会**造进化腔（easy 64s / normal 79s）并研究（easy 局拿到 `melee_attacks` 1 级）。
但第一版测试写的是「normal 难度跑 300 秒」，而**被动挨打的玩家在 128 秒就被推平了**，`step()` 在 `game_ended` 后不再推进 AI——于是测出来的是「玩家太脆」，不是「AI 不研究」。
修法：用 easy 难度 + 给玩家基地周围放 12 个陆战队员，并把「AI 造出科技建筑」和「AI 拿到升级」拆成两条断言，失败时能区分是「没造建筑」还是「造了不研究」。

### 9.7 满级攻防下的兵种定位（本轮补上的空白）

`Matchup.gd` 原来只覆盖 0 级状态，「双方都升满之后兵种定位还在不在」没有数据。
本轮给 `Matchup.gd` 加了**第二轮跑**：同一批 11 个对位，双方所有升级线拉满再跑一遍，
断言与基线相同。测试项从 12 → **23**。

结果：**11 个对位胜负关系全部不变，只有残兵数微调。**

| 对位 | 0 级 | 满级 |
|---|---|---|
| 1 狂热者 vs 4 跳虫 | A 胜，剩 1 | A 胜，剩 1 |
| 2 狂热者 vs 4 陆战队员 | A 胜，剩 1 | A 胜，剩 **2** |
| 6 跳虫 vs 1 狂热者 | A 胜，剩 **4** | A 胜，剩 3 |
| 其余 8 项 | — | 完全相同 |

**解读**：升级是**同向**增强，没有把任何一对关系打反。神族拿到的是
「地面护甲 +3 **且** 等离子护盾 +3」两条线（比另外两族多一层，与 SC1 一致），
所以在 2 狂热者 vs 4 陆战队员这种多打少的对位里残兵更多 —— 方向符合预期，
量级也可接受（没有出现「满级后神族 1 打 5」这种碾压）。

`research` / `upgrade` / `cmd_ability` **命中数为 0** —— 平衡对局里双方都没在用新系统。
它证明的是「加了升级系统后原有平衡没被打破」，**不能**替代「双方都升满的完整对局」。
