## 二、★两个「不报错」的真 bug★

这一轮最重要的产出不是法术本身，而是**两个只有专门测试才抓得到的 bug**。
两个都不报错、都不崩、都不影响「能不能玩」，只让**伤害数字悄悄少一点**。

### 2.1 区域到期，吞掉最后一跳

**症状**：心灵风暴 4 秒 / 每 0.5 秒一跳 = 应该是 **8 跳**，实测只打出 **7 跳**，
总伤害 **77 而不是 88**（少 12.5%）。

**原因**：`_tick_spell_zones()` 里**先判到期、后结算**：

```gdscript
# ❌ 错的顺序
z["remain"] -= delta
if z["remain"] <= 0.0:
    spell_zones.remove_at(i)     # ← 区域在这里被整片删掉
    continue
_zone_dot_tick(z)                # ← 第 8 跳永远走不到
```

`remain` 与「已过去的时间」是**同时**走到终点的。第 80 帧（0.05 步长）时
`remain` 正好归零、第 8 跳也正好该打 —— 先判到期的话，第 8 跳在
「**已经攒满、还没来得及打**」的状态下被整片删掉。

**修法**：**先结算，再判到期**。

这种偏差最难发现：它不是崩溃，也不是「技能没效果」。
平衡测试跑起来只会觉得「风暴好像没那么强」，然后去调 `dps` —— 越调越偏。

### 2.2 dot 跳数随帧率漂移（根因是**浮点尾数的方向**）

**症状**：改完 2.1 之后，`0.02s` 步长打出 88 点，`0.05s` 步长打出 77 点。
同一份代码、同一段时间，**只因为帧率不同就少了 12.5% 的伤害**。

**第一层原因**（好找）：累加器 `acc += delta` 的浮点漂移。
`0.05` 累加十次未必 `>= 0.5`，于是第一次结算落到第 11 帧，
整条时间线往后偏移一格，4 秒只打出 7 跳。

**第二层原因**（真正的根因，也是最难找的）：`remain` 反复减 `delta` 之后，
**带一个方向不定的浮点尾数**。实测：

| 步长 | 跑满 80 帧后 `remain` | 符号 |
| --- | --- | --- |
| `0.05` | `+5.842548667089886e-15` | **正** |
| `0.02` | `−3.28e-15` | **负** |

正的尾数让 `duration - remain` 差一点点**不到** `4.0`：

```
floor(3.9999999999999942 / 0.5) = 7      ← 少一跳
```

这就是「`0.05` 步长少一跳、`0.02` 步长正常」的真正原因 ——
不是累加器的问题，是**同一个减法在不同步长下产生相反方向的误差**。

**修法（两处，缺一不可）**：

1. **跳数由「已过去的时间」推导，绝不用累加器**：
   `int(floor(_effect_elapsed(z) / DOT_TICK))`
2. **`const SPELL_EXPIRE_EPS := 1.0e-6`** + `_effect_elapsed()` 在到期帧
   一律返回 `duration`（按「整整活满」算），把浮点尾数彻底排除出决策。

```gdscript
func _effect_elapsed(e: Dictionary) -> float:
    var dur := float(e.get("duration", 0.0))
    var remain := float(e.get("remain", 0.0))
    return dur if remain <= SPELL_EXPIRE_EPS else dur - remain
```

### 2.3 两个 bug 的症状**互为镜像** —— 这是区分它们的唯一线索

| 坏法 | `0.02s` 步长 | `0.05s` 步长 |
| --- | --: | --: |
| 先判到期（2.1） | **77** ❌ | 88 ✅ |
| 累加器漂移（2.2） | 88 ✅ | **77** ❌ |

两者都是「总伤害 77」，都是「少一跳」，**但坏在不同步长上**。
如果只测一种步长，两个 bug 里必定漏掉一个。这也是为什么
`tests/Spell.gd` 里那条「帧率无关」断言要**同时跑两种步长并逐点比较**。

### 2.4 顺带修掉的第三个：`apply_effect` 拉长时长不清 `ticks`

dot 的跳数是由 `duration - remain` 推出来的。补一发辐照时 `duration` 被拉长、
但 `ticks` 没清零 → `duration - remain` 变成**负数** → 新的一轮 dot **一跳都不打**。

**症状**：**补一发辐照反而把伤害补没了**。玩家只会觉得「这技能是不是有 bug」。

```gdscript
if new_dur > old_dur:
    c["ticks"] = 0        # ← 必须清零
c["duration"] = new_dur
```

## 三、三层结构：区域 / 状态 / 施法者

### 3.1 为什么不是一个 `effects` 数组

法术在战场上留下的东西有**两种**，生命周期完全不同：

| | 战场区域 | 状态效果 |
| --- | --- | --- |
| 存在哪 | `World.spell_zones` | `Unit.effects` |
| 中心在哪 | **固定在战场上** | 跟着单位走 |
| 谁受影响 | 每帧重新查询范围内单位 | 只有被挂上的那个单位 |
| 例子 | 心灵风暴 / 黑暗虫群 | 辐照的 dot |

一个单位走进风暴圈 → 被 dot；走出去 → dot 继续（已经挂上了）。
黑暗虫群反过来：**区域不动、单位走出去就免疫了**（还留 0.35 秒残留，
免得「一只脚在圈外」的那一帧漏一发）。

**⚠️ `spell_zones` 不能叫 `effects`** —— 那个名字已经被「爆炸特效」占用了。

### 3.2 结算顺序

```
World.step(delta)
  ├── _tick_spell_effects(delta)      ← 在单位更新**之前**
  │     ├── _tick_spell_zones(delta)
  │     └── _tick_unit_effects(delta)
  ├── _update_units()                 ← 移动 / 攻击 / 采集
  └── ...
```

放在前面是因为：**法术结算会打死人**。先结算的话，这一帧死掉的单位
不会再被 `_update_units` 当作活人处理（少一次「已经死了还在开火」的窗口）。

### 3.3 `DOT_TICK = 0.5` —— 为什么不是「每帧 `dps × delta`」

每帧结算的话，同样的 `dps` 在 30 帧下和 144 帧下**总伤害一样，但跳数不一样**。
而 `take_damage()` 里有 `maxf(1.0, ...)` 的**地板**（每跳至少 1 点）：

> 144 帧下每帧跳一次，`28 dps` 会变成 `144 × 1 = 144` 点/秒 —— **5 倍**。

所以 dot 必须按**固定间隔**结算。`0.5` 秒一跳 = 4 秒 8 跳，
每跳 `28 × 0.5 = 14` 点，扣掉护甲后约 11 点。

## 四、三个法术

### 4.1 心灵风暴 —— 「敌我不分」是**特性**，不是 bug

星际 1 的心灵风暴会**打死自己人**。这不是设计缺陷，是它之所以强的原因之一：
乱丢会自伤，所以「什么时候丢、丢在哪」才有技术含量。

`affects: "all"` 时 `_zone_apply_damage()` 的 `owner` 参数**必须留 -1**
（不按阵营过滤）。测试里专门有一条「圈内自己人也掉血」守这个行为。

**AI 侧相反**：`_ai_storm_spot()` 里有 `hit_friend` 检查 —— **AI 不许往自己人头上丢**。
两件事不矛盾：AI 要像个正常人，玩家要有完整的操作空间（包括自己坑自己）。

### 4.2 黑暗虫群 —— 判「远程 vs 近战」，不是判「谁在里面」

`blocked_by_dark_swarm(shooter, target)` 三个条件**同时**成立才挡：

1. **目标是地面单位**（空中单位不受影响）
2. 目标带 `no_ranged` 效果
3. **攻击者 `_weapon_reach() > MELEE_RANGE`(60)** ← 关键

第 3 条是最容易写错的地方。**不能只判「攻击者在不在圈里」** ——
那会把近战也一起挡掉，虫群变成**无敌圈**。星际 1 的虫群挡的是「远程火力」，
近战该打得进还得打得进。

**⚠️ 对空中火力同样有效**。这是星际 1 里它对抗飞龙的原因。
写测试时我第一版把方向写反了（断言「飞行单位能打虫群里的地面单位」）——
那会**逼着实现开后门**。已改成 `_test_swarm_blocks_air_too()`，并配了
「把猎物挪出虫群后必须打得中」的阳性对照。

**闸门要加在所有开火点**：单位开火（`_update_combat`）与建筑开火
（`_update_building_combat`）各一处，且必须在 `u.cooldown = ...` **之前**。
放在后面的话冷却照扣、只是不造成伤害 —— 表现成「兵在原地反复抬手但打不出东西」。

### 4.3 辐照 —— 传染

`_apply_dot_tick()` 里按 `spread_radius`(44px) 找**同阵营**单位挂**同样时长**的效果。
注意是「同阵营」不是「敌方」—— 星际 1 里辐照会顺着**友军**传染，
所以正确的应对是把被辐照的兵**单独拉开**，而不是扎堆。

## 五、触屏施法 UI

### 5.1 瞄准态复用「放置建筑」的手势

点技能键 → 进入瞄准态 → 按下拖动选落点 → 松手施放。**和放置建筑是同一套手势**
（共用 `_aim_drag_id`）。重新发明一套的话，两处的手势边界
（拖出屏幕、点到自己人身上、双指缩放）迟早不一致。

### 5.2 预览圈画的**就是**施法半径

```gdscript
var ar := float(asp.get("radius", 40.0)) * cam_zoom     # 预览
var rr := float(zd["radius"]) * cam_zoom                # 落地后的区域
```

**同一个数**。另写一个「好看一点」的预览半径，玩家会按预览圈去估范围，
然后发现打不到边上的人 —— 而且他会以为是自己的问题。

截图实测：预览圈半径 ≈ **55px** = `52 × 1.05`（`cam_zoom`），与落地后的风暴圈**重合**。

### 5.3 射程环 + 够不着就整体转红

以**施法者**为中心画 `cast_range` 环，让玩家一眼看出「这个落点够不够得着」。
够不着 → 预览圈和提示条**整体转红**，提示文案换成「超出施法距离 · 靠近一点再放」。

**触屏上没有悬浮提示，颜色是唯一的手段。**

### 5.4 `_guard_aim_state()` —— 每帧自愈

选中部队里没人能放这个法术 → 自动退出瞄准态。

靠「在每个选择变更调用点都记得清 `_aim_spell`」是不可维护的
（本项目有十几个选择变更点）。漏一处的症状是
「**瞄准圈一直挂着、点哪都放不出来**」，而且不报错。

### 5.5 技能键第二行显示「能量 N」，不是冷却

法术的 `cooldown: 1.0` 是**防触屏连点**用的（触屏上双击很容易发生，
没有它的话一次点击能把 200 点能量一次倒空），**不是平衡数值**。
真正卡住玩家的是能量 —— 显示冷却等于什么都没说。

### 5.6 三种状态效果环

| 效果 | 画法 | 颜色 |
| --- | --- | --- |
| `dot` | 脉动的环，`elapsed` 驱动 | 绿 `(0.62, 1.0, 0.45)` |
| `no_ranged` | 实线 + 一段加亮的虚边 | 紫 `(0.70, 0.55, 0.95)` |
| `slow` | 蓝白链环，越慢越实 | 蓝白 `(0.60, 0.82, 1.0)` |

**⚠️ `slow` 目前没有任何法术产出** —— 它是给后续法术（比如虫族女王的诱捕网）
留的基础设施，本轮只做了「系统 + 渲染」，靠 `apply_effect` 直接挂验证。
截图 `37_effect_rings` 是专门为它开的特写。

## 六、联机：协议 v1 → v2

### 6.1 快照要传什么

| 新增字段 | 编码 | 理由 |
| --- | --- | --- |
| 单位 `energy` | `u8` 整点 | `roundi` 往返精确。用比例会有累积误差 |
| 单位 `effects` | id 索引 / kind 索引 / `remain`×100 | 状态效果必须同步，否则两端「谁能打谁」不一致 |
| 法术区域 | id / owner / x / y / `remain`×100 | 放在快照**尾部** |

### 6.2 法术区域**不传半径和时长**

半径与时长由收包方从本地 `GameData.SPELLS` **重建**。省带宽是次要的，
主要是**保证两端数值一致** —— 模组改了 `radius` 时，如果传过来的是施法方的数值，
接收方画出来的圈和实际判定就会对不上。

### 6.3 ⚠️ 解码时**直接赋值** `u.effects = efs`，不走 `apply_effect()`

走 `apply_effect` 的话，「**同源不叠加**」逻辑会把刚还原的效果**合并掉**，
往返就对不上了。快照还原要的是「**逐字节还原**」，不是「按规则重放」。

### 6.4 `PROTOCOL_VERSION` 升到 2

**⚠️ 在尾部追加字段同样会让旧版本读错位** —— 旧版本不知道后面还有东西，
但它按自己的长度读完后就会去读下一个单位的字段。所以版本号必须升，
不能靠「加在后面就兼容」。

### 7.4 ★测试自身的四处判据错误★

这一轮**测试自己错了四次**，每一次都会让断言假红或恒真：

1. **「敌我不分」的靶子摆错了**：用狂热者 + 蟑螂当靶子且只相距 **14px**
   → 两者**自己先打起来**，「敌人掉 80」里绝大部分是近战伤害。
   **修法**：改成两个相距 100px 的**探机**（射程 36，谁也够不着谁，护甲护盾完全相同）。

2. **断言方向写反**：断言「飞行单位能打虫群里的地面单位」。
   星际 1 的黑暗虫群**对空中火力同样有效** —— 这条断言会逼着实现开后门。
   **修法**：改成「空中远程也打不进」，并配阳性对照。

3. **测试场里施法静默失败**：快照测试场把蝎子放在落点 **500px 外**
   （施法距离 200）→ `cmd_ability` 静默失败 → 「往返一致」「字节相同」
   **三条断言一起变成恒真**。
   **修法**：距离缩到 210px 内 + 补一条「**前提：区域真的落下来了**」的断言。

   > **凡是「先施法、再断言」的测试，都要先断言施法成功。**

4. **`--check-only` 的退出码不可靠**：语法错误时仍可能返回 0。
   判断依据一律是 grep 日志里的 `SCRIPT ERROR|Parse Error|Compile Error`。

### 7.6 ★全量回归抓到的 7 条失败：新增单位会打破**别人的**不变量★

第一次跑全量回归时 `rc=1` —— 7 条失败，**没有一条在 Spell 套件里**，

| 套件 | 失败断言 | 根因 |
| --- | --- | --- |
| Build | 全部 22 个建筑 + 20 个单位都有介绍 | 3 条新 `desc` **超过 20 字** |
| Air | 介绍文案不超过 20 字 | 同上 |
| Air | terran 的空中单位都有攻击力 | 科学球 `damage: 0`（支援单位） |
| Air | 每个单位/建筑都有专属造型 | **3 个新单位没有程序化贴图**，落进兜底圆盘 |
| Net | ★视野内的敌方单位在快照里★ | 测试里**手抄了一份**单位记录布局，v2 改了它没跟上 |
| Net | 阳性对照：不过滤时敌方单位都在 | 同上（解析错位） |
| Net | ★玩家自己的单位一个都没被过滤掉★ | 同上（解析错位） |

**这一节的教训比修法本身重要**：

1. **「加个单位」从来不是加个单位。** 它会同时撞上
   **介绍文案长度上限 / 空中单位的攻击力约束 / 程序化贴图的兜底分支 /
   联机协议的字段布局** 四套既有不变量。这些约束**每一条都是对的**
   —— 它们各自守着一个曾经踩过的坑。所以正确的做法是**逐条去满足**，
   而不是去改宽约束。

   唯一「改宽」的是「空中单位必须有攻击力」：科学球**本来就该是零攻击**
   （星际 1 也是这样）。但我没有简单删掉这条断言，而是改成
   **「支援单位豁免，但必须有技能」** —— 把原来的意图
   （不许出现「不能打、也不能放技能」的死配置）**保住了**。

2. **★测试里手抄一份数据布局，迟早会跟丢★。**
   `tests/Net.gd` 原本逐字段 `r.u32r(); r.u16r(); ...` 手工跳过单位记录。
   v2 在记录尾部加了 `energy` + 效果列表，每个单位多 2 字节
   → 从第二个单位起全部错位 → 三条断言变红，而**产品代码完全正确**。

   修法不是「把缺的字段补上」（下次还会跟丢），而是**别再抄一份布局**：
   直接调生产解码器 `Net.apply_snapshot()` 解进一份临时世界，再读它的单位表。
   **「快照里有哪些单位」从此只有一个定义。**

3. **程序化贴图的兜底分支是静默的。** 新单位没写造型 → 画成一颗圆盘，
   不报错、不警告。`GenTex.last_was_fallback` 这个「兜底就置位」的机制
   （见 `godot-procedural-sprite-qa`）正是为了把这种静默变成可断言。
   本轮 3 个单位的造型都补上了，并新出放大图 `24_zoom_units_m5`。

   > 三条只有放大图能验的造型约束：
   > 圣堂武士**不能有灵能刃**（否则和狂热者分不出来）、
   > 蝎子必须**扁而宽**（否则和跳虫、蟑螂糊成一团）、
   > 科学球**不能有炮管**（否则和幽灵战机混淆）。

## 九、接下来的方案

按**「不做就会一直悬着」**排序，不是按技术难度。

### 9.1 真机验证（**从 M4c 悬到现在，仍然是第一优先**）

联机这条线从 M4a 到 M4c 写了 19 套测试、1400+ 条断言，
但**两台真设备从来没对打过一局**。

> 无头测试能证明「协议编解码往返一致」，**证明不了**「两台手机在同一个
> 家用 WiFi 下能发现对方、能连上、能打完一局」。

具体要验的：

1. `NetDiscovery` 的 UDP 广播在真实 WiFi 下能不能互相看见（很多路由器**隔离客户端**）
2. ENet 握手在 4G / 弱网下会不会卡在 `CONNECT_TIMEOUT`
3. 触屏手势在真机上和模拟器的差异（尤其双指缩放与框选的边界）
4. **安卓后台切换**：切出去再回来，ENet 连接还在不在

### 9.2 法术的「下一步深度」

现在只有 3 个法术，且都是「点地 / 点人」两种最简形态。星际 1 里还有：

- **护盾电池 / 治疗波**（对友军施放，`kind: "target_ally"` —— 系统已支持 `heal`）
- **诱捕网 / 地震**（`slow` 已经实现但**没有产出方**，正好接上）
- **召唤类**（蜘蛛雷 / 孵化幼虫 —— 需要「法术生成单位」这条新路径）
- **反馈**（对能量单位造成「能量值」伤害 —— 需要读目标能量，是新判定）

### 9.3 平衡

三个法术的数值（`75 能量 / 52 半径 / 28 dps`）是**照着星际 1 的手感拍的**，
没有跑过对局验证。真正要做的是一次「法术对抗」的 matchup 测试：
1 个圣堂武士能换掉几个跳虫？虫群能让多少飞龙白给？

### 9.4 性能

`_tick_spell_zones` 每帧遍历所有区域、每个区域再查一次范围内单位。
现在最多 3~5 个区域无所谓，但如果以后有「召唤流」或「地雷阵」，
需要改成**空间哈希查询**（`query_units_near` 已经是哈希了，但区域本身没索引）。

### 9.5 存档 / 回放

协议 v2 的快照已经是「完整状态」了 —— 它离**回放**只差一个「按帧存快照」。
把快照写进文件就是一个能拖时间轴的回放系统。
